# 결정 기록

## 2026-11-16 회원관리·소셜 로그인을 main 위로 옮김 (design/iphone-mobile c001cbb → 0012)
- 옮긴 것: 이메일 가입·아이디/이메일 로그인, Google(PKCE)·Kakao 로그인, `users.role`·`status`, 승인제, 관리자 회원관리 API(`/v1/admin/members*`), `app.tools.create_user`. 마이그레이션은 main의 0011 뒤 `0012`로 새로 썼다. 옮기지 않은 것: 브랜치의 배포 구성·관리자 대시보드·`admin_audit_log`(main의 `admin_access_log`에 적는다)·목록의 사용량 수치·웹 화면.
- 브랜치와 다르게 한 것: ① 대기 계정은 세션을 받지 못한다(가입 202, 로그인 403 `account_pending`) — 브랜치는 로그인시키고 API만 막았다. ② 세션을 읽을 때 사용자 상태를 함께 봐서 정지 즉시 쿠키·Bearer가 끊긴다. ③ OAuth state를 서버에 두고 한 번만 쓴다(쿠키에는 state만). ④ 소셜 계정은 **확인된 이메일끼리만** 묶는다(`users.email_verified`) — 이메일 가입 계정에 묶던 브랜치의 선점 위험을 없앴다. ⑤ 첫 소셜 로그인도 초대 코드·동의를 따른다. ⑥ 카카오도 시크릿 필수.
- 관리자 규칙: `role == admin` 또는 `ADMIN_USERNAMES`(기존 동작 그대로). 관리자는 자기 자신을 정지·강등·삭제할 수 없고, `ADMIN_USERNAMES`의 계정은 API로 정지·삭제할 수 없다 → API로는 관리자가 0명이 되지 않는다.
- 기본값은 예전 동작: 승인제 꺼짐(`AUTH_SIGNUP_REQUIRES_APPROVAL=false`), 소셜 로그인 꺼짐(ID·시크릿이 모두 있어야 켜짐). 운영 모드는 소셜을 켜면 `PUBLIC_BASE_URL`(https)을 요구한다.
- 확인 못 한 것: 실제 Google·Kakao 왕복(가짜 제공자·모의 HTTP로만 검증). 이메일 소유 확인(메일 발송)은 없다 — 이메일 가입자는 소셜 연결이 안 된다.
- 2026-11-17 보안 검토 반영: OAuth state 보관소는 가득 차도 남의 것을 버리지 않는다(클라이언트당 20개, 전체가 차면 새 시작 거절) · 활성 관리자가 0명이 되는 변경·삭제·본인 탈퇴는 409 `last_admin`(변경과 한 트랜잭션, 권고 잠금) · `PATCH …/members/{id}`의 `expected_status`(다르면 409 `member_changed`) · 회원관리 기록에 결과(`_done`·`_failed`)와 거절(`member_refused`)을 남기고 대상은 줄인 id만 · Caddy 로그에서 `code`·`state` 가림 · 이메일은 ASCII·DNS 모양만 · `create_user`는 입력을 가릴 수 없는 터미널(Git Bash)에서 비밀번호를 받지 않는다.
- 알려진 한계(M1, 정책 미정): 주소를 확인하지 않는 이메일 가입으로 남의 주소를 먼저 차지할 수 있다 — 진짜 주인의 Google·Kakao 로그인은 `auth_error=email_in_use`, 이메일 가입은 409가 된다. 이메일 확인(메일 발송)이 있어야 풀린다. 그때까지는 관리자가 선점한 계정을 지운다.
- 알려진 한계(M2, 정책 미정): main에서 온 이름 단독 실패 한도(5 × `AUTH_NAME_FAILURE_FACTOR`)가 이메일에도 걸려, 알려진 이메일은 주소 네 곳에서 틀리면 15분 잠긴다. 선택지: `AUTH_NAME_FAILURE_FACTOR=0`, 또는 이름 단독 범위만 넘었을 때는 맞는 비밀번호를 통과시키기(여러 주소로 나눠 추측하는 것에 대한 상한이 약해진다).
- 알려진 한계(L7): `APP_ENV=production`이 아니면 헤더 스텁(`AUTH_ALLOW_HEADER_STUB` 기본 true)이 회원 상태 검사를 건너뛰고, `PUBLIC_BASE_URL`이 비면 redirect_uri를 Host 헤더로 만든다. 운영 모드는 스텁이 켜져 있으면 시작하지 않는다.
- 알려진 한계(main과 달라진 동작): `DELETE /v1/auth/me`가 소셜 전용 계정에는 빈 비밀번호를 받는다 · 계정마다 로그인 실패 제한 키가 둘이다(아이디와 이메일) · 권한 관리자가 다른 사람을 관리자로 올릴 수 있다.

## 2026-11-16 말투 프로필 리뷰 반영 — 존댓말끼리는 혼용이 아니다, 건수 문턱 없음, 묻는 카드는 맞음이 아니다

## 2026-11-17 묶음 첨삭 `POST /v1/rewrites/batch` — 같은 초안을 여러 상대에게(1~5명)

- 화면: 첨삭 화면에서 상대를 더하면 묶음, 한 명이면 예전 단건 그대로. 웹 단위 테스트는 이 PC에서 못 돌렸다(node 없음).

## 2026-11-17 회원·소셜 로그인 이식이 두 갈래로 겹쳤다 — `port/members-mobile`(PR 8)을 기준으로
- 배경: 같은 날 두 세션이 `design/iphone-mobile`의 회원관리·소셜 로그인을 서로 모르고 main 위로 옮겼다 — `feat/members-social-login`(PR 7, 백엔드만)과 `port/members-mobile`(PR 8, 백엔드 + 모바일 웹·관리자 회원 화면·로그인 화면). 둘 다 `0012_members_social_login`을 만들고 18개 파일에서 충돌해 하나만 기준이 될 수 있다.
- 결정: PR 8을 기준으로 하고 PR 7은 닫는다. 화면이 PR 8의 API 계약(`/v1/auth/providers`, 승인 대기 202, `expected_status`, 409 코드 넷)에 맞춰져 있고, PR 8에만 마지막 관리자 보호(경합 포함)·서버에 두는 일회용 OAuth state·DB CHECK 제약·`email_verified`·엄격한 이메일 검증·`create_user`가 있다. 독립 비교(bf72296 대 52eb979)에서 PR 7의 계정 가로채기·소셜 가입 동의 누락이 재현됐는데, PR 7은 그 뒤 `11042e5`에서 둘을 고쳤다 — 그래도 위 차이는 남는다.
- PR 7에서 가져온 것: 운영 검사의 `PUBLIC_BASE_URL`을 경로 없는 `https://도메인`으로 제한(앞머리만 보던 것), 백로그 A10. 가져오지 않은 것: 쿠키에 두는 state(재시작에 강하지만 일회용·서버 만료를 잃는다), 로그인 실패를 계정 기준으로 세기(아이디·이메일을 번갈아 틀릴 때의 한도 — PR 8은 키가 둘이라 두 배다. 잠금으로 이메일과 아이디의 짝이 드러나는 문제와 저울질이 필요해 따로 정한다).
