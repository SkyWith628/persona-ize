# 정답 데이터셋 만들기 가이드 (팀원용)

코딩 지식이 없어도 읽고 따라 할 수 있게 썼습니다. 모르는 말이 나오면 맨 아래 **용어 풀이**를 보세요.
(2026-11-08 갱신: 등장인물 표가 `evals/characters.csv` 파일이 되었고, 메시지 번호 형식이 `대화방:번호`로 바뀌었습니다.)

## 1. 우리가 왜 이걸 만드나요?

우리 서비스는 사용자가 쓴 메시지를 **상대에 맞는 말투로 고쳐 주되, 내용(날짜·약속·사람 등)은 절대 바꾸지 않는** 서비스입니다.

그런데 AI가 잘 고쳤는지는 **"정답지"가 있어야** 채점할 수 있습니다. 시험에 문제와 답안지가 필요한 것과 같습니다. 오늘 만드는 것이 바로 그 문제와 답안지입니다.

이 데이터는 다음 일에 쓰입니다.

- AI가 **사실을 바꾸지 않았는지** 자동으로 검사
- 과거 대화를 찾아오는 방식 두 가지(단순 검색 vs 지식그래프)의 **성능 비교**
- 공모전·포트폴리오에서 "정말 더 좋아졌다"는 **증거**

## 2. 만들 것은 세 가지입니다 (섞지 마세요)

| 구분 | 무엇인가 | 비유 | 담당 | 저장 위치 |
|---|---|---|---|---|
| ① 등장인물 표 | 상대가 누구고 내가 어떻게 말하는지 | **출연진 명단** | 다 같이 (15분) | `evals/characters.csv` |
| ② 가짜 과거 대화 | 우리가 지어낸 카톡 같은 대화 | AI가 읽는 **참고서** | 사용자·시나리오 담당 | `data/synthetic/` |
| ③ 평가 사례 | 문제(초안)와 답안지(지켜야 할 것) | **시험 문제 + 답안지** | 평가·품질 담당 | `evals/eval_cases.csv` |

지식그래프 담당은 ②를 같이 보면서 "여러 대화에 흩어진 사건을 연결해야 풀리는 장면"을 요청합니다.

## 3. 반드시 지킬 약속 3가지

1. **진짜 대화를 넣지 않습니다.** 실제 있었던 일에서 영감을 받더라도 이름·날짜·장소는 모두 바꿉니다. 이 데이터는 외부 AI 서비스(Claude, Neo4j)로 전송됩니다.
2. **등장인물은 ①의 표를 따릅니다.** 대화마다 이름이 달라지면 AI가 같은 사람인지 알 수 없습니다. 단, "지현 팀장님" / "팀장님" / "박지현 님"처럼 **호칭이 여러 가지로 불리는 것은 일부러 넣어도 좋습니다.** 그래프가 한 사람으로 합치는지 시험하는 재료가 됩니다.
3. **파일은 UTF-8 CSV로 저장합니다.** 엑셀에서 저장할 때 "CSV UTF-8" 형식을 고르세요. 그냥 CSV로 저장하면 한글이 깨집니다. 구글 시트를 쓰면 "다운로드 → CSV"로 받으면 됩니다.

PR을 올리면 자동 검사(`scripts/validate_data_files.py`)가 열 이름·값·메시지 번호를 확인해 줍니다. 빨간 표시가 나면 메시지를 읽고 고치면 됩니다.

## 4. 1단계: 등장인물 표 (15분, 다 같이)

파일 `evals/characters.csv`가 이 표입니다. 사용자 본인은 **김민수**이고, 지금 들어 있는 상대는 넷입니다.

| name (인물) | relation (나와의 관계) | my_speech_style (나는 이렇게 말한다) | aliases (그 사람을 부르는 말) |
|---|---|---|---|
| 박지현 | 팀장 | 존댓말, 정중함 ("~드리겠습니다") | 지현 팀장님 ; 팀장님 ; 박지현 님 |
| 이서연 | 동기 | 반말 → 10/17 파트장 발령 뒤 공식 자리에선 존댓말 | 서연 ; 서연아 ; 서연 파트장님 |
| 김준호 | 동생 | 편한 반말, 장난스러움 (ㅋㅋ) | 준호 ; 야 |
| 최유진 | 친구 | 반말, 친함 | 유진 ; 유진아 |

- 우리 평가 계획이 **관계 4종** 기준이므로 처음에는 이 넷으로 충분합니다. 인물을 더 넣을 때는 `relationship_type` 열(코드가 쓰는 영어 분류: superior/colleague/subordinate/friend/family/partner/acquaintance)도 팀장과 함께 채웁니다.
- 아래 ③ 평가 사례의 `relation` 열에는 이 표의 `relation` 값(팀장/동기/동생/친구)만 씁니다.

## 5. 2단계: 가짜 과거 대화 쓰기 (시나리오 담당)

### 쓰는 법
- 인물마다 **말투가 확 다르게** 씁니다. 말투가 다 비슷하면 "말투 맞춰 고치기"를 시험할 수 없습니다.
- 한 대화방에 5~10줄 정도, 날짜와 시간을 붙입니다.
- 대화에 **날짜, 약속, 부탁, 사과**가 자연스럽게 들어가게 합니다.
- 일부는 일부러 **사건이 여러 대화방에 나뉘게** 씁니다. 예를 들어 서연이가 파트장이 된 소식은 동기 방에, 그 뒤 존댓말로 바뀐 업무 대화는 같은 방의 며칠 뒤에, 팀장 방에는 그 발표 자료 얘기가 나오게 하는 식입니다. 지식그래프가 필요한 사례를 만드는 핵심입니다.

### 어디에 어떻게 쓰나
- 구글 시트나 엑셀에 **대화방 / 번호 / 날짜시간 / 말한 사람 / 내용** 다섯 열로 씁니다. 말한 사람은 `me`(나) 또는 `contact`(상대) 둘 중 하나입니다.
- 저장 형식(JSON)은 [data/synthetic/README.md](../../data/synthetic/README.md)에 있습니다. 변환은 팀장이 `scripts/csv_to_synthetic.py`로 합니다 — 시트를 **CSV UTF-8**로 내려받아 PR에 붙이면 됩니다. 열 이름은 그대로(대화방·번호·날짜시간·말한 사람·내용), '상대' 열을 하나 더 두면 대화방마다 누구와의 대화인지 적을 수 있습니다. 말한 사람은 `me`/`contact` 또는 이름.
- 지금 들어 있는 대화: `data/synthetic/sample_conversations.json` (대화방 4개, 36줄). 먼저 읽어 보고 같은 느낌으로 이어 쓰세요.

### 메시지마다 번호가 있습니다
나중에 "이 사례에는 이 메시지가 도움이 된다"고 가리킬 때 필요합니다. 형식은 **대화방id:메시지id** 입니다.

| 대화방 | 대화방id | 메시지 번호 예 |
|---|---|---|
| 박지현 팀장 방 | c1 | c1:m03 |
| 김준호 동생 방 | c2 | c2:m05 |
| 이서연 동기 방 | c3 | c3:m05 |
| 최유진 친구 방 | c4 | c4:m06 |

새 대화방을 만들면 다음 번호(c5, c6…)를 쓰고, 메시지는 그 방 안에서 m01부터 붙입니다.

### 예시 (동기 방, c3)
```
c3:m05 | 2026-10-17 17:40 | contact | 민수야 나 다음 주부터 너네 파트 파트장으로 발령났어 ㅠ
c3:m06 | 2026-10-17 17:42 | me      | 헐 축하해!! 근데 이제 회사에선 존댓말 써야겠네 ㅋㅋ
c3:m08 | 2026-10-21 10:05 | me      | 서연 파트장님, 오늘 스탠드업 회의록 공유드립니다.
```

### 예시 (팀장 방, c1)
```
c1:m10 | 2026-10-14 09:02 | contact | 수고했어요 민수씨. 다음 달 워크숍 발표도 민수씨가 맡아줄래요?
c1:m11 | 2026-10-14 09:15 | me      | 네 팀장님, 맡겠습니다. 자료는 11월 5일까지 드리겠습니다.
```

"서연이가 10/17에 파트장이 됐고 그 뒤로는 존댓말"이라는 사실은 c3의 여러 날짜에 흩어져 있습니다. 이런 장면이 **지식그래프 사례**입니다.

## 6. 3단계: 평가 사례 쓰기 (평가·품질 담당)

사례 하나가 `evals/eval_cases.csv`의 **한 줄**입니다. 열은 다음과 같습니다.

| 열 | 뜻 | 쓰는 법 |
|---|---|---|
| case_id | 사례 번호 | E001, E002, ... 순서대로 |
| relation | 받는 사람 | 1단계 표의 relation 값: 팀장 / 동기 / 동생 / 친구 |
| situation | 상황 한 줄 | 일정 지연 양해, 거절, 사과, 부탁, 일정 조율 중 하나 |
| original_text | 사용자가 쓴 **어색한 초안** | 실제로 급하게 쓸 법한 말투 그대로 |
| preserve_items | 바뀌면 안 되는 내용 | `종류=내용`을 `;`로 이어 쓰기 (아래 설명) |
| must_not_change | 하나라도 바뀌면 **무조건 실패**인 것 | preserve_items 중 가장 중요한 것을 **그대로 복사** |
| expected_notes | 좋은 첨삭의 조건과 나쁜 예 | 한두 문장 |
| needs_graph | 여러 대화를 연결해야 풀리는가 | Y 또는 N |
| relevant_msg_ids | 이 사례에 도움이 될 과거 메시지 번호 | `c3:m05;c3:m08` 처럼 `;`로 구분. 없으면 비움. **Y면 꼭 채움** |
| as_of | 이 초안을 쓰는 시점 | 2026-10-22 같은 날짜. 이 날짜 **이후** 대화는 참고할 수 없음 |
| split | 연습용인지 시험용인지 | dev(연습) 또는 test(시험). 아래 참고 |

### `preserve_items` 쓰는 법
"바뀌면 안 되는 것"을 `종류=내용` 형식으로 씁니다. 종류는 아래 중에서만 고르세요. 사람마다 다르게 쓰면 자동 검사를 못 합니다.

- `날짜` / `시간` / `수량` / `금액`
- `사람` (누가 하는지)
- `행동` (무엇을 하는지)
- `가능여부` (할 수 있다 / 없다)
- `약속` / `조건`

예: `날짜=내일 오전;행동=자료 보냄`

### `split` 정하는 법
- **dev**: 우리가 AI를 고치면서 계속 들여다보는 연습 문제
- **test**: 마지막 채점에만 쓰는 시험 문제. 고칠 때 보면 안 됩니다.

사례 5개 중 1개 꼴(20%)을 test로 정하고, 정한 뒤에는 바꾸지 않습니다. 시험 문제를 미리 보고 공부하면 점수가 부풀려지기 때문입니다.

### 사례 예시 1 (일반)
| 열 | 값 |
|---|---|
| case_id | E001 |
| relation | 팀장 |
| situation | 일정 지연 양해 |
| original_text | 오늘 정리해서 내일 오전까지 보내드릴게요. |
| preserve_items | 날짜=오늘;날짜=내일 오전;행동=자료 보냄 |
| must_not_change | 날짜=내일 오전 |
| expected_notes | 존댓말로 정중하게. 시간을 "오늘 중"이나 "내일 오후"로 바꾸면 실패 |
| needs_graph | N |
| relevant_msg_ids | (비움) |
| as_of | 2026-10-14 |
| split | dev |

### 사례 예시 2 (지식그래프가 필요한 경우)
| 열 | 값 |
|---|---|
| case_id | E004 |
| relation | 동기 |
| situation | 사과 |
| original_text | 어제는 제가 좀 예민했던 것 같아요. 미안합니다. |
| preserve_items | 날짜=어제;행동=사과 |
| must_not_change | 행동=사과 |
| expected_notes | 서연이 10/17 파트장 발령 뒤라 존댓말이 맞음. 구체적 사유를 지어내면 실패 |
| needs_graph | Y |
| relevant_msg_ids | c3:m05;c3:m06;c3:m08 |
| as_of | 2026-10-22 |
| split | dev |

### 사례 쓰는 순서 (추천)
1. 2단계의 가짜 대화에서 **장면 하나**를 고른다.
2. 그 장면에서 사용자가 급하게 쓸 법한 **어색한 초안**을 쓴다.
3. 초안에서 **바뀌면 안 되는 것**을 `preserve_items`에 적는다.
4. 그중 가장 중요한 것 하나를 `must_not_change`에 복사한다.
5. 도움이 될 과거 메시지 번호를 `relevant_msg_ids`에 적는다.

## 7. 오늘의 목표

**관계 4종 × 상황 5종 = 20칸에 사례 1개씩**, 합쳐서 20개를 목표로 합니다. (최종 목표는 칸마다 6개씩 총 120개)

- 20개 중 **최소 5개는 `needs_graph=Y`** 로 만듭니다.
- 오늘 안에 못 채워도 괜찮습니다. 양식을 통일하고 **각자 1건씩 시범으로 쓰고 서로 보는 것**이 오늘의 진짜 목표입니다.

### 서로 검토하기
쓴 사람과 **다른 사람**이 확인합니다.

- 평가 담당 → 시나리오 담당의 사례: "이 내용을 자동으로 검사할 수 있나?"
- 시나리오 담당 → 평가 담당의 사례: "사람이 정말 이렇게 쓰나?"

## 8. GitHub에 올리는 법 (GitHub Desktop 기준)

1. GitHub Desktop에서 **Fetch origin** → **Current Branch → New Branch**를 눌러 `역할/내용` 형식으로 이름을 정합니다. (예: `eval/cases-week1`, `scenario/convos-week1`)
2. 자기 폴더의 파일을 수정하고 저장합니다.
3. GitHub Desktop 왼쪽에 바뀐 파일이 보이면 아래 칸에 한 줄 설명을 적고 **Commit**을 누릅니다.
4. **Push origin**을 누르고, 이어서 나오는 **Create Pull Request**를 누릅니다.
5. 팀장이 확인한 뒤 합칩니다. `main`에 직접 올리지 마세요.

간단한 문서나 CSV 한 줄 수정은 GitHub 웹사이트에서 연필 아이콘으로 바로 고쳐도 됩니다.

## 9. 자주 하는 실수

- 초안이 너무 정돈되어 있다 → 실제로는 급하게 줄여 쓰고 말투도 섞입니다. 어색하게 쓰세요.
- 모든 사례가 날짜 하나만 보존 대상이다 → 사람, 가능여부, 약속, 조건도 골고루 넣으세요.
- `needs_graph=Y`인데 `relevant_msg_ids`가 비어 있다 → 어떤 메시지를 연결해야 하는지가 정답이므로 꼭 채웁니다. (자동 검사가 막습니다)
- `must_not_change`를 새로 써서 `preserve_items`와 글자가 다르다 → 복사해서 붙입니다.
- 가짜 대화 속 이름과 표의 이름이 다르다 → 1단계 표(`characters.csv`)를 기준으로 합니다.

## 용어 풀이

- **초안**: 사용자가 처음 쓴 메시지. AI가 고치기 전 상태.
- **첨삭**: 글을 고쳐 주는 것. 여기서는 말투를 상대에 맞게 바꾸는 일.
- **보존 항목**: 말투가 바뀌어도 절대 변하면 안 되는 내용(날짜, 약속 등).
- **지식그래프**: 사람·사건·관계를 선으로 이은 지도 형태의 저장 방식. "서연은 10/17부터 파트장, 그 뒤 존댓말" 같은 정보를 이어 줍니다.
- **검색(C) vs 그래프(D)**: 과거 대화를 찾아오는 두 가지 방법. C는 비슷한 문장을 찾고, D는 사람·사건 관계를 따라 찾습니다. 어느 쪽이 나은지 비교하는 것이 우리 프로젝트의 핵심 실험입니다.
- **dev / test**: 연습용 / 시험용 문제.
- **PR(Pull Request)**: "내 수정사항을 합쳐 주세요"라는 요청.
- **UTF-8**: 한글이 깨지지 않게 저장하는 파일 형식.
