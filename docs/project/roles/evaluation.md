## 어떻게 하나

1. **사례 쓰기 순서**: 과거 대화(시나리오 담당)를 먼저 읽는다 → "이 장면 다음에 내가 보낼 법한 초안"을 쓴다 → 보존 항목을 `종류=값` 형식으로 적는다(`날짜=내일 오전;가능여부=금요일 불가`) → 어떤 변화가 실패인지 `expected_notes`에 한 문장 → 과거 대화가 필요한 사례면 `needs_graph=Y`와 `relevant_msg_ids`(`c1:m03;c1:m04`) → `as_of`(사용자가 보내는 날짜).
2. **보존 규칙 대조**: 팀장이 `run_eval.py` 결과 CSV를 주면 `violations`·`first_attempt_violations` 열을 본다. 규칙이 못 잡은 변경(예: "금요일은"→"금요일까지는")이 있으면 `preserve_rules.md`에 유형을 추가하고 PR에 사례 번호를 적는다.
3. **루브릭**: 5점 척도 축을 4~5개로 제한. 각 점수에 **실제 결과 문장 예시**를 붙인다(11/08 실측 메모 `evals/results/*.md`의 출력 표를 가져다 써도 된다). "자연스러움"은 마지막에, 사실 보존은 루브릭에서 빼고 규칙으로만.
4. **블라인드 시트**: 팀장이 `scripts/make_blind_sheet.py build`로 조건을 숨기고 섞은 CSV(`evals/blind/*-sheet.csv`)를 준다. 같은 사례에서 결과 문장이 같은 조건은 한 줄로 합쳐지고 원문 자체도 한 줄 들어간다(기준선). 채점 열(격식·친근함·호칭·길이·자연스러움 1~5, 사실_의심 Y/N, 메모)을 채워 `*-sheet.scored.csv`로 저장해 PR. 채점자는 평가 담당 + 시나리오 담당 + 가능하면 외부 1명. 채점 뒤 팀장이 정답 키로 조건을 붙여 비교표를 만든다.

## 반드시 지킬 것
- **사실 보존 실패는 다른 점수로 상쇄하지 않는다.** 말투가 아무리 좋아도 날짜가 바뀌면 그 사례는 실패다.
- 사례의 `relation`은 `characters.csv`의 값(팀장/동기/동생/친구…)만. 열 이름을 바꾸면 코드가 깨지니 PR에 적는다.
- test split 사례는 팀장도 개선에 쓰지 않는다. dev로만 고치고 test로 확인한다.

## 팀장에게 요청할 때
- 결과 CSV의 열 뜻이 모호하면 Issue. `evals/README.md`에 설명이 있다.
- 새 보존 유형을 코드에 넣어 달라 → `preserve_rules.md`에 유형·예시 3개를 먼저 적고 PR.
