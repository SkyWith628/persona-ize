## 1. 목적과 근거 구분

**상대와 상황에 맞는 사용자의 말투를 적용하되, 원문의 사실과 의도를 보존하는 메시지 첨삭 서비스.**

- [자료] 3~7쪽: 관계마다 다른 사회적 역할과 말투, 표현 조정의 인지적 부담이 문제다.
- [자료] 11~15쪽: 관계별 페르소나 저장과 유사한 과거 대화 활용이 차별점이다.
- [자료] 16~21쪽: 상대 선택 → 페르소나 설정 → 메시지 작성 → 추천 확인 → 입력창 적용.
- [자료] 22~31쪽: Orchestrator, GraphDB Updater, History Retriever, Message Rewriter를 제안한다. 대화 기록 DB와 지식 그래프를 분리하고 사용자가 결과를 검토한다.
- [자료] 32쪽: 일관성, 지연, 작업 성공, BERTScore, 사용성, 설문을 제안한다.
- [자료] 33~36쪽: 소통 부담 완화와 플랫폼 대상 B2B 라이선스 모델을 제시한다.

- [미확인] 시장 규모·설문 비율과 B2B 수요는 검증하지 않았다. 발표자료의 통계를 사업성 검증 결과로 간주하지 않는다.

## 2. 초기 사용자와 검증할 가설

초기 대상은 상사·동료에게 부탁, 거절, 일정 조율 메시지를 자주 쓰는 대학생·취업준비생·사회초년생이다. 처음부터 모든 관계와 모든 글쓰기를 다루지 않는다.

핵심 가설:
1. 관계별 설정이 일반적인 ‘정중하게 수정’보다 사용자 선호를 높인다.
2. 본인이 실제 작성한 과거 표현을 추가하면 페르소나만 사용할 때보다 ‘나다운 말투’ 평가가 높아진다.
3. 그래프 검색의 추가 비용은 관계·사건 연결이 필요한 사례에서만 정당화될 수 있다.

성공 경험: 사용자가 상대를 선택하고 초안을 입력하면 사실이 보존된 제안을 받아 소폭 수정하거나 그대로 적용한다.

## 3. 범위와 사용자 흐름

MVP (최소 기능 제품): 핵심 가설을 검증할 수 있는 가장 작은 제품.

| 기능 | MVP | 이후 |
|---|---|---|
| 관계별 페르소나 | 상대별 직접 설정·수정 | 상황별 세부 프로필 |
| 과거 대화 | 명시적 업로드, 미리보기, 본인 화자 지정 | 검증된 외부 연동 |
| 첨삭 | 원문 + 상황 + 최근 맥락 + 본인 발화 예시 | 그래프 기반 사건 검색 |
| 결과 | 추천 1개, 변경 이유, 사실 경고, 적용·취소 | 복수 후보 비교 |
| 피드백 | 적용 여부·수정량·거절 이유 | 사용자 승인 후 프로필 갱신 |
| 메시지 전송 | 복사·자체 입력창 적용 | 외부 플랫폼 승인 후 별도 검토 |

메인 화면: 상대 목록 / 페르소나 편집 / 대화 가져오기 / 작성 화면 / 추천 비교 / 데이터 관리.

1. 계정 생성 후 상대를 등록한다. 이름 대신 별칭 사용 가능.
2. 상대와의 관계, 원하는 격식·친근함·길이·이모지·금지 표현을 설정한다.
3. 선택적으로 대화 파일을 업로드한다. 파싱 미리보기에서 화자와 대화방을 확인한다.
4. 원문과 상황을 입력하고 추천을 요청한다.
5. 추천과 바뀐 부분, 의미 변경 경고를 확인한다.
6. 적용 또는 직접 수정한다. 적용은 외부 전송과 구분한다.
7. 저장 동의가 있는 경우에만 피드백을 기록한다.

데이터가 없으면 설정만으로 동작한다. 과거 대화를 필수 가입 조건으로 만들지 않는다.

## 4. 권장 아키텍처와 선택 이유

RAG (검색 증강 생성): 필요한 과거 대화를 검색해 모델 입력에 포함하는 방식.
ICL (문맥 내 학습): 모델 가중치를 바꾸지 않고 입력 예시로 스타일을 유도하는 방식.

초기 구성:

```text
React + TypeScript 웹
        │ HTTPS
        ▼
FastAPI: 인증·소유권·검증·사용량 제한
        │
        ├─ PersonaService / ImportService / FeedbackService
        └─ RewriteWorkflow
             ├─ 입력·의도·보존 항목 확인
             ├─ 관계 범위 내 과거 예시 검색
             ├─ LLM 첨삭
             └─ 출력 검증 → 통과 또는 1회 재생성
        │                         │
        ▼                         ▼
PostgreSQL + pgvector       LLM / Embedding Provider
        ▲
        │
Import Worker: 파싱·비식별화·대화 묶음 생성·임베딩

2단계 실험: Graph Extractor → Neo4j → 제한된 그래프 검색
```

| 선택 | 이유 | 대안과 Trade-off |
|---|---|---|
| React + TypeScript | 자체 작성 UI에 집중 | Next.js는 서버 렌더링 필요 시 검토 |
| FastAPI | Python AI 처리와 API를 한 언어로 구현 | Node 백엔드 추가는 언어 경계·운영 부담 증가 |
| PostgreSQL + pgvector | 관계 데이터·메타데이터·벡터를 한 DB에서 관리 | MySQL+별도 벡터 DB는 익숙할 수 있으나 동기화 대상 증가 |
| 고정된 워크플로 | 순서와 실패 지점이 명확하고 평가하기 쉬움 | 자율 에이전트는 동적 도구 선택에 유리하나 비용·재현성 부담 |
| 선택적 LangGraph | 상태 전이·재시도·중단 추적 필요 시 사용 | 최초는 Python 함수 조합으로도 충분 |
| GraphDB 후속 실험 | 원자료의 그래프 가설을 검증 가능하게 유지 | 초기부터 Neo4j를 추가하면 추출·삭제·정합성 부담 증가 |
| 사전학습 API 모델 | 데이터 없는 시점에도 기준선 확보 | 자체 미세조정은 동의받은 충분한 데이터와 별도 품질 검증 필요 |

LangGraph 공식 문서는 고정 경로를 갖는 워크플로와 동적으로 동작하는 에이전트를 구분한다. 이 서비스의 초기 첨삭 경로는 고정형에 가깝다.
https://docs.langchain.com/oss/python/langgraph/workflows-agents

pgvector는 PostgreSQL에서 벡터 유사도 검색을 제공한다. 초기 데이터량에서는 소유권·관계 조건으로 범위를 좁힌 정확 검색부터 시작하고, 규모가 증가하면 인덱스와 필터 조합의 검색 품질을 측정한다.
https://github.com/pgvector/pgvector

## 5. AI 처리 설계

### 5.1 가져오기: 사용자 요청과 분리한 비동기 작업

업로드 → 크기·형식 제한 → 파싱 → 화자 확인 → 민감정보 처리 → 중복 제거 → 대화 묶음 생성 → 임베딩 → 검색 준비 완료.

- 최초는 UTF-8 텍스트와 정의된 JSON 형식만 지원한다. 실제 카카오 내보내기 형식은 샘플 확보 후 별도 어댑터로 구현한다.
- 원본 시간·화자·대화방·메시지 ID를 보존한다. 같은 파일 재업로드는 해시와 원본 식별자로 중복 방지한다.
- 자신의 발화만 문체 예시로 사용한다. 상대방 발화는 필요한 주변 맥락으로만 사용한다.
- 대화는 문장 고정 길이보다 2~6개 턴의 맥락 단위로 묶는 것을 초기 실험값으로 한다. 토큰 상한도 함께 둔다.
- 실패 메시지를 건너뛰고 성공으로 처리하지 않는다. 실패 행 수와 재시도 가능 여부를 표시한다.
- 임베딩 모델·차원·전처리 버전을 기록한다. 모델 교체 시 기존 벡터와 혼합하지 않고 재색인한다.

### 5.2 관계별 페르소나

상대별 레코드에 관계 유형, 격식, 친근함, 직접성, 선호 길이, 이모지 빈도, 선호·금지 표현, 자유 설명을 저장한다. 수치 범위는 UI에서 설명하고 검증한다.

사용자가 원하는 표현과 실제 과거 말투가 충돌하면 명시적 현재 설정을 우선한다. ‘정중함’ 하나의 점수로 모든 스타일을 압축하지 않는다. 관계 유형은 사용자가 설정하며 대화에서 민감한 성격 특성을 추정하지 않는다.

프로필 변경은 버전으로 관리한다. 과거 생성 결과에는 사용한 버전을 연결한다. 피드백 한 번으로 프로필을 자동 덮어쓰지 않는다.

### 5.3 요청 시 워크플로

1. **검증:** 인증 사용자로 소유권을 확인하고 빈 원문·길이·상황 값을 검증한다. user_id는 요청 본문에서 신뢰하지 않는다.
2. **의도·보존 항목:** 부탁/거절/사과/일정 조율 등 의도를 구분한다. 날짜, 수량, 사람, 가능·불가능, 약속, 조건을 보존 항목으로 만든다. 규칙 추출과 필요 시 구조화 모델 추출을 결합하되 추출 결과도 오류 가능성을 가진다.
3. **검색:** 동일 사용자·동일 상대를 기본 범위로 삼는다. 현재 요청 이전 데이터만 대상으로 한다. 사실 맥락과 본인 문체 예시를 역할별로 구분하고 출처·화자·시점을 보존한다. 검색 맥락은 현재 원문의 사실을 자동 덮어쓰지 않는다. 원문 의미·상황 유사도로 후보를 찾고 중복을 줄인다. 초기 top-k=3~5는 조정할 실험값이다. 별도 DB나 두 번의 모델 호출은 필수가 아니다.
4. **프롬프트 구성:** 시스템 규칙 → 현재 사용자 설정 → 현재 원문·최근 맥락 → 검색 예시 순으로 경계를 명시한다. 과거 예시는 문체 자료이며 현재 사실의 근거가 아니다.
5. **생성:** 원문 사실과 의도를 유지하며 문체만 조정한다. 과거 대화에 등장한 사유·날짜·이름을 새 원문에 추가하지 않는다.
6. **검증:** 구조화 출력 스키마, 날짜·수량·고유명사 변화, 부정·가능성·약속 변경, 금지 표현을 검사한다. 필요 시 별도 의미 비교 평가를 보조로 사용한다.
7. **분기:** 통과하면 추천을 표시한다. 실패하면 구체적인 위반 항목을 전달해 최대 1회 재생성한다. 다시 실패하거나 모델 장애가 나면 원문을 유지하고 추천 실패를 표시한다.
8. **사용자 검토:** 추천을 적용해도 자동 전송하지 않는다. 요청 시작 후 초안이나 상대가 바뀌었으면 결과를 자동 적용하지 않는다.

예시: 원문 “오늘 정리해서 내일 오전까지 보내드릴게요.”의 문체는 바꿀 수 있지만, ‘오늘은 정리가 어렵다’, ‘내일 오후에 보내겠다’라는 사실을 추가하면 실패다.

예산 초안: 원문 2,000자, 최근 맥락과 검색 예시를 포함한 입력 6,000토큰 이내, 출력 800토큰 이내. 전체 요청 20초 제한, 모델 재생성 1회 이내. 모델별 한도·요금·실측 후 조정한다. 재시도에도 동일 사용자 예산을 적용한다.

내부 출력 예시:

```json
{
  "rewritten_text": "첨삭된 문장",
  "change_reasons": ["호칭과 종결 표현을 상대별 설정에 맞췄습니다."],
  "evidence_ids": ["episode_123"],
  "warnings": []
}
```

서버는 evidence_ids가 실제 검색된 동일 사용자 자료인지 검증한다. 모델의 ‘의미 보존 성공’ 자기 보고를 최종 판정으로 사용하지 않는다.

### 5.4 GraphRAG 확장 실험

GraphRAG (그래프 기반 검색 증강 생성): 개체 사이 관계를 탐색해 필요한 근거를 찾는 방식.

그래프 후보: Person, Conversation, Message, Event. 관계 후보: SENT, IN_CONVERSATION, MENTIONS, ABOUT_EVENT. 모든 노드·관계에 소유자와 원문 출처를 연결한다. 추출된 사실과 사용자 확정 사실은 구분한다.

LLM이 생성한 임의 쿼리를 실행하지 않는다. 서버의 허용된 쿼리 템플릿으로 동일 사용자·상대 범위와 최대 1~2홉, 결과 개수 제한을 강제한다. 원문 삭제 시 파생 노드·관계도 삭제한다.

도입 조건: 여러 메시지에 흩어진 동일 사건을 연결하는 평가셋에서 단순 검색 대비 개선이 있고, 기본 말투 첨삭에서 비용·지연 손해를 감당할 수 있을 때. 그래프는 관계 구조를 보존하지만 문체 신호를 자동으로 잘 보존하는 것은 아니다. 최종 문체 예시는 원문 발화를 다시 조회한다.

각 사용자 데이터는 user_id 조건과 서버 소유권 확인으로 격리한다. 연결된 contact/conversation/persona도 같은 소유자인지 검증한다. DB 제약 또는 복합 외래키로 교차 사용자 연결을 방지한다. 외래키·인덱스는 실제 조회 패턴에 맞춘다.

제약: `(contact_id, version)` 유일, `(user_id, idempotency_key)` 유일, import의 사용자·대화방·원본 식별자 중복 방지. 삭제는 원문, 에피소드, 임베딩, 그래프, 캐시까지 추적한다. 생성 이력에 개인정보가 남는 보존 정책도 함께 정의한다.

## 7. API 초안

인증은 검증된 라이브러리로 처리하고, 브라우저 세션은 HttpOnly·Secure 쿠키를 기본으로 검토한다. 쿠키 기반 쓰기 요청은 CSRF 방어를 적용한다. 직접 비밀번호 인증을 구현한다면 Argon2/bcrypt, 세션 만료·폐기까지 필요하다.

| 메서드·경로 | 기능 |
|---|---|
| POST /v1/contacts | 상대 생성 |
| GET /v1/contacts | 상대 목록 |
| PUT /v1/contacts/{id}/persona | 새 페르소나 버전 저장; 기대 버전으로 충돌 감지 |
| POST /v1/conversations | 대화방 생성 |
| POST /v1/conversations/{id}/imports | 파일 업로드; 202 + job_id |
| GET /v1/imports/{id} | 처리 상태·실패 사유 |
| POST /v1/rewrites | 추천 요청; Idempotency-Key 사용 |
| GET /v1/rewrites/{id} | 추천 결과 조회 |
| POST /v1/rewrites/{id}/feedback | 적용·수정·거절 피드백 |
| DELETE /v1/conversations/{id} | 원문·파생 검색 데이터 삭제 요청 |
| GET /v1/deletion-jobs/{id} | 삭제 완료·실패 확인 |

첨삭 입력: contact_id, conversation_id(선택), draft_text, draft_version, situation, persona_version. 사용자 식별자는 인증에서 결정한다.

일반 오류: 401 인증 필요, 403 접근 불가, 409 버전 충돌·동일 키 다른 본문, 422 입력 오류, 429 사용량 초과, 503 모델 일시 장애. 같은 키·같은 본문 재요청은 기존 결과 또는 진행 상태를 반환하며 중복 과금 작업을 방지한다.

MVP는 완성된 검증 결과를 반환한다. 추후 스트리밍은 검증 전 문장이 입력창에 적용되지 않게 설계한다.

## 8. 평가와 완료 기준

아래 수치는 **초기 합의용 목표**이며 실측 결과가 아니다.

### 비교 실험

A: 원문 + 일반 첨삭 지시.
B: A + 상대별 페르소나.
C: B + 검색한 본인 과거 표현.
D: C + 그래프 검색.

C 내부에서는 최신·무작위·키워드·의미 검색을 비교한다. 검색 없음보다 항상 좋아진다고 가정하지 않는다. D는 다른 사용자 기록을 추가하지 않고 C와 같은 개인 기록 범위에서 그래프 효과를 측정한다.

동일 평가 입력·모델·생성 예산을 사용한다. 각 사례는 최소 3회 생성해 변동을 관찰한다. 학습/개발/평가를 사용자 및 대화·시간 단위로 분리하고, 평가 정답·미래 메시지가 검색 저장소로 유입되지 않게 한다. 초기 120사례(관계 4종 × 상황 5종 × 사례 6개)와 별도의 적대적·장애 테스트를 준비한다. 실제 일반화 주장은 더 많은 사용자 평가가 필요하다.

### 지표

| 단계 | 지표 | 초기 목표·해석 |
|---|---|---|
| 검색 | Recall@5 | 사람이 지정한 유용한 예시 회수율 0.8 이상 목표; 정답 집합 정의 필요 |
| 생성 | 핵심 사실 보존 | 일반 평가셋 98% 이상 목표; 중요 날짜·금액·약속 변경 사례는 출시 차단 |
| 생성 | 관계·스타일 적합성 | 블라인드 5점 평가 평균 4점 이상 목표 |
| 생성 | 개인화 효과 | C가 A보다 선호되는 비율 60% 이상 목표; 표본 수·신뢰구간 병기 |
| 제품 | 적용·수정량 | 제안 적용률과 적용 후 수정량을 함께 측정; 추적 동의 필요 |
| 운영 | 지연·비용 | p50/p95·요청당 토큰/비용 기록; p95 8초 목표는 실측 후 조정 |
| 보안 | 사용자 격리 | 교차 사용자 검색·조회·변경 테스트 전부 통과 |

BERTScore는 의미 유사도 보조 지표다. 부정, 수량, 기한, 약속의 미세한 변경을 별도 검사해야 한다. 반복 출력의 문자열 동일성도 품질과 다르므로, 동일 입력에서 사실 보존과 스타일 기준 통과율을 측정한다.

모델 평가기는 보조 수단이다. 평가 기준을 고정하고 사용자 본인의 블라인드 선호 및 사람 검토와 대조한다. 자신의 말투 적합성은 제3자만으로 확정하지 않는다.

회귀 테스트: 빈 입력, 공백, 긴 문장, 이모지, 한국어 존댓말·반말 혼합, 모순된 페르소나, 예시 없음, 상대 발화 혼입, 다른 사용자/상대 기록, 수량·날짜·부정, 프롬프트 공격, 중복 요청, 초안 변경 후 늦은 응답, API 타임아웃·429, 삭제 후 검색.

## 9. 개인정보·운영·장애

- 업로드 전 저장·외부 모델 전송·재사용 목적을 분리해 안내하고 동의를 받는다. 제3자 대화는 최소한만 처리하며 공유 데모는 합성·비식별 데이터로 만든다.
- 파일 크기·확장자·실제 형식을 확인한다. 원본 파일명은 저장 경로로 쓰지 않는다.
- 원문·검색 문서의 지시는 데이터로만 취급한다. 모델이 권한이나 검색 범위를 바꿀 수 없게 한다.
- 로그에는 요청 ID, 단계, 토큰 수, 지연, 오류 코드만 기본 기록한다. 대화 원문과 프롬프트를 외부 추적 도구에 자동 전송하지 않는다.
- 결과는 텍스트로 렌더링해 스크립트 실행을 막는다. SQL은 매개변수 바인딩을 사용한다.
- API 키는 서버 환경변수·비밀 저장소에서 읽으며 프론트에 포함하지 않는다. 요청 횟수와 일일 토큰 예산을 제한한다.
- 원문 보존 기간·삭제 처리 기한·백업 잔존 기간은 베타 공개 전 확정한다. MVP 제안은 명시적 동의 없으면 첨삭 원문·출력을 장기 보존하지 않는 정책이다.
- 검색 장애는 사용자에게 이력 미사용 상태를 알리고 페르소나만으로 축소 동작할 수 있다. 인증·소유권 검증 실패는 축소 동작 없이 중단한다.
- 모델 장애나 검증 실패는 원문 유지로 대응한다. 재시도는 제한하고 반복 실패는 운영 지표로 추적한다.
- 삭제 요청 시 먼저 검색 대상에서 제외하고 파생 데이터 삭제를 수행한다. 실패 작업은 재시도하며 완료 상태를 확인할 수 있게 한다.

10배 확장 시: 부하 측정 → API와 가져오기 워커 분리 → 사용자별 동시 실행·토큰 제한 → 벡터 인덱스 품질 검증 → 필요 시 큐 도입 순으로 진행한다. 사용자의 원문·상대·프로필 버전이 섞이지 않게 캐시 키를 설계한다. 세부 배포 서비스는 목표 트래픽과 예산을 확인한 후 별도 결정한다.

## 11. 구현 순서와 단계별 완료 조건

인원·기간이 미정이므로 아래는 4주 기준의 가안이다. 일정 확정이나 납기 보장이 아니다.

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| 1주차 | 범위 확정, 합성 사례 20개, A/B 실험, 관계·프로필 CRUD | 과거 기록 없이 입력→추천→수동 적용 성공; 의미 보존 검토 |
| 2주차 | 업로드·화자 지정·대화 묶음·벡터 검색 | C 실험 가능; 중복 업로드와 소유권 테스트 통과 |
| 3주차 | 사실 검증·재생성·피드백·삭제·사용량 제어 | 장애 시 원문 유지; 삭제 후 검색 차단; 주요 회귀 통과 |
| 4주차 | 120사례 평가·사용자 검토·데모 정리 | A/B/C 비교 보고서, 지연·비용 보고, 한계 공개 |
| 후속 | 그래프 추출·D 실험 | C 대비 개선과 추가 비용을 근거로 채택/보류 |

가장 먼저 만들 수직 기능: **상대 1명·페르소나 1개·원문 1개 → 첨삭 → 사실 검사 → 직접 적용.** 이 흐름이 확인되기 전 대규모 대화 수집과 그래프 구축부터 시작하지 않는다.

## 12. 착수 전에 확정할 사항

현재 설계는 신규 독립 웹 프로젝트, 한국어, 1:1 관계, 텍스트 메시지, API 모델 사용을 가정한다.

확정 필요: 개인/팀 및 인원, 실제 기간, 월 API 예산, 데모/운영 목표, 사용 가능한 동의받은 데이터, GraphRAG가 필수 과제인지 여부. GraphRAG가 필수라면 MVP 이후로 제외하는 대신 단순 검색과 그래프 검색을 나란히 구현해 비교하는 범위로 조정한다.

## 14. 관련 논문 검토에 따른 결정 기록

상세 근거: [관련 논문 검토 및 설계 적용 판단](literature-review.md), 2026-10-28.

1. **개인화 검색은 가설로 검증:** LaMP의 과제·설정별 차이를 고려해 페르소나만 사용하는 기준선을 유지한다.
2. **맥락·스타일 분리:** 검색 예시의 용도를 구분하고 과거 날짜·사유가 현재 메시지로 복사되는 오류를 검사한다. 이 원칙은 WeStar·LongMemEval을 참고한 프로젝트 적용안이며 논문 구현을 그대로 복제하는 것은 아니다.
3. **그래프는 제한 실험:** PersonaAgent with GraphRAG는 분류·평점 과제의 결과다. 관계별 문체 성능의 직접 근거로 쓰지 않으며 커뮤니티의 다른 사용자 대화를 가져오는 구조는 채택하지 않는다.
4. **스타일 설정은 설명 가능하게:** Style-Eliciting Prompts·Drift를 참고해 수정 가능한 속성을 유지한다. 전용 디코더 학습이나 토큰 제어는 후속이다.
5. **품질 평가 확대:** 개인 문체·상대 적합성·자연스러움·수정 부담을 분리하고, 사실 보존 실패는 다른 점수로 상쇄하지 않는다. 사용자 단위 집계와 불확실성을 보고한다.
6. **증거 수준 구분:** 합성 사례는 기능 검증에 유용하지만 실제 개인화 효과를 입증하지 않는다. 본인 작성 예시와 동의받은 사용자 평가가 필요하다.

모델·검색 실험은 아직 실행하지 않았다. 위 결정은 문헌을 바탕으로 한 설계 판단이다.
