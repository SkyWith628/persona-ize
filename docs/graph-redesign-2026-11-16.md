# 지식그래프 재설계: 상대별 말투에 닿는 그래프

**요약.** 지금 그래프는 첨삭 문장에 거의 닿지 않습니다. 오늘 실측에서 문장을 바꾼 경로는 "그래프 → 사용자가 승인한 설정" 하나뿐이었습니다. 그래서 그래프의 역할을 "초안과 비슷한 사실을 찾아 주는 검색기"에서 "상대별 말투 상태를 유지하고, 바뀐 이유와 함께 설정 변경을 제안하는 장치"로 바꿉니다. 말투·호칭처럼 메시지 표면에서 보이는 것은 규칙으로 계산합니다. Graphiti 그래프는 규칙이 못 하는 일, 즉 말투가 바뀐 계기(예: 파트장 발령)와 적용 범위 단서(예: "사적으로는 편하게 하자")를 찾는 일을 맡습니다. 가장 앞에 내세울 결과는 첨삭 문장이 아니라 "제안이 사람이 쓴 정답 설정과 얼마나 맞는가"입니다. 이 문서의 설계는 아직 실행·검증되지 않았고, 오늘의 실측, 코드 구조 조사, 논문 조사, 두 건의 비평을 종합한 것입니다.

표기: **필수**(대회 전 반드시), **권장**(첫 결과가 좋으면), **나중에**(대회 이후). 근거는 **[실측]**(우리 데이터), **[논문]**(논문이 직접 보인 것), **[판단]**(팀의 판단, 근거 논문 없음)으로 구분합니다.

## 1. 지금 무엇이 문제인가 (실측)

오늘 측정(Opus 5.5, 평가 5건 × 3회 반복, 대화방 4개의 합성 메시지 36개)에서 확인된 것입니다.

- **C와 D의 문장이 거의 같았습니다.** 그래프는 경고에만 나타났습니다(이전 약속, 같은 날 회의). 관련 메시지 recall은 한 건에서 0.50 → 1.00, 나머지는 동일했습니다.
- **읽는 열쇠가 틀렸습니다.** 말투를 정하는 상태를 "초안과의 유사도"로 찾기 때문에, 사과 초안에 "파트장님이라 부르고 존댓말을 쓴다"가 아니라 점심 제안이 나왔습니다.
- **전달 형태가 틀렸습니다.** 상태가 자유 문장의 "사실"로 전달되는데, 프롬프트는 사실 문맥을 내용으로 쓰지 못하게 합니다. 구조화된 속성은 프롬프트에 들어가지 않습니다.
- **출처가 불안정합니다.** 말투 속성이 메시지 단위 LLM 추출에서 나오는데 실행마다 바뀝니다(팀장/팀장님, colleague/acquaintance, closeness는 자주 null). 무효화된 사실 26개 중 11개는 유효해진 지 1시간 안에 무효화된 추출 부산물이었고, 여전히 참인 사실도 무효로 표시됐습니다.
- **문장을 바꾼 경로는 설정이었습니다.** 그래프 기반 제안을 적용하자(격식 3→4, 호칭 없음→'파트장님') 3회 모두 "...예민했던 것 같아요. 정말 미안해요."가 "파트장님, 어제는 제가 좀 예민했던 것 같습니다. 죄송합니다."로 바뀌었습니다. 단, 한 건에서만 확인했습니다.
- **그래프가 필요한 평가 건은 5건 중 1건입니다.**

초안의 두 표현은 비평에 따라 고칩니다.

- "관찰된 변화가 해요체 → 합쇼체라서 지금 enum으로 표현할 수 없다"는 틀린 서술이었습니다. 데이터(c3)의 변화는 반말 → 합쇼체이고 지금의 반말/존댓말 enum으로 표현됩니다. "미안해요 → 죄송합니다"는 사용자 이력의 변화가 아니라 격식 3과 4의 첨삭 결과 차이입니다. 3단계 구분(합쇼체/해요체/해체)은 변화 감지가 아니라 격식 3과 4 중 무엇을 제안할지 고르는 데 필요합니다.
- "문헌이 C ≈ D를 예측한다"는 과한 표현이었습니다. 영어 질의응답 연구(Zep의 DMR, Mem0의 LoCoMo)는 짧은 이력에서 메모리 시스템이 전체 문맥을 넣는 것보다 낫지 않다고 보고합니다. 방당 10개 메시지 규모에서 검색 효과가 없는 것은 유추로 보면 놀랍지 않지만, 말투에 대해 이를 측정한 논문은 없습니다.

## 2. 설계 원칙과 근거

| # | 원칙 | 근거 |
|---|---|---|
| P1 | 말투 상태는 상대 id로 읽는다. 초안과의 유사도로 읽지 않는다. | **[실측]** 점심 제안 오검색. **[판단]** 상대 id로 읽는 것은 우리 선택이다. Zep, GraphRAG, LightRAG는 개체별 요약·프로필을 기록 시점에 만들고 MemGPT는 작은 블록을 항상 문맥에 두지만, 이 논문들은 "id로 읽기"를 시험하지 않았고 말투도 다루지 않는다. Bell 1984(초록만 읽음)는 수신자가 문체의 일차 요인이라는 이론적 배경이다. |
| P2 | 표면에서 보이는 말투 사실은 규칙으로 뽑는다. LLM은 표면에 없는 것만 추출한다. | **[실측]** 실행 간 뒤바뀜. **[논문]** Atil 2024: 호스팅 LLM의 실행 간 변동은 정상이다(질의응답류 과제에서 정확도 차이 최대 15%, 추출 과제는 아님). Danescu-Niculescu-Mizil 2013: 영어 요청문에서 해석 가능한 표면 단서와 학습된 분류기로 공손성의 상당 부분을 잡는다(같은 도메인은 사람보다 약 3점 낮고, 다른 도메인은 11~13점 낮다). **한국어 어미·호칭 규칙이 정확한지는 증명되지 않았고, 1주차 분류기 검사가 그것을 잰다.** |
| P3 | 추론 단위는 상대(메시지를 모은 것)이고, 근거 메시지 id를 남긴다. | **[논문]** DialogRE: 대화 속 관계의 약 96%가 여러 문장의 근거를 요구하고 최고 모델이 55~61 F1이다(영어 대본). Power Networks: 쌍의 메시지를 모으는 설정(영어 이메일). |
| P4 | "현재 값"은 코드가 결정론적으로 정한다. 세밀도는 현재 / 이전 / 언제부터. | **[실측]** 무효화 26개 중 11개가 부산물이다. `invalid_at`을 믿지 않는 결정은 이 측정에만 근거한다. **[논문, 간접]** MemoryAgentBench(영어, 매우 긴 문맥의 합성 사실 수정): 단일 홉 충돌 해결에서 검색·메모리 시스템은 대략 50%대 이하이고(HippoRAG-v2 54, MemGPT 28, Mem0 18, GraphRAG 14), 긴 문맥 모델만 그보다 높다. 논문 판에 따라 수치가 달라(예: BM25 56 또는 48) 발표 자료에 쓰기 전에 표를 다시 읽어야 한다. Graphiti 무효화의 정확도를 잰 것은 아니다. Jiang 2026(초록만 읽음, GitHub·Wikipedia 데이터): 거친 현재/대체 상태 유지와 표시 형식을 맞춘 대조군을 권한다. 그 연구에서는 거친 무효화가 현재 상태 질의에 도움이 됐으므로 이 논문은 "무효화를 믿지 말라"의 근거가 아니다. Reddy 2026(초록만 읽음): 현재값 정책을 생성 밖에 둔다. |
| P5 | 프롬프트에 닿는 것은 사용자의 원문 발화다. 추출 사실이 원문을 대체하지 않는다. | **[논문]** LongMemEval, HippoRAG 2: 영어 질의응답 검색에서 원문을 추출 사실로 바꾸면 정보가 손실된다. **[판단]** 프로필 구간으로 문체 예시를 고르는 것은 우리 가설이고, 이를 시험한 논문은 없다. |
| P6 | 말투 단계는 이산값(합쇼체/해요체/해체)이고 규칙으로 잰다. | **[판단]** 3단계 목록과 규칙 분류기는 우리 설계 선택이며, 격식 3과 4를 가르기 위해 필요하다. LoCar(초록만 읽음, 차량 비서 응답)는 "LLM의 한국어 높임 제어가 불안정하니 명시적으로 확인해야 한다"까지만 뒷받침한다. |
| P7 | 위계와 친밀도는 별개 축이다. 표면에 없는 속성은 제안 전용이다. | **[논문]** Park 2025(한국어, 객관식 12문항): 모델이 위계보다 친밀도에서 사람과 더 어긋난다. Power Networks: 지도학습으로도 위계 방향은 약 80~83%다. |
| P8 | 호칭은 승인된 설정을 통해서만 첨삭에 들어간다. | 고정 원칙. **[실측]** 3/3 사례. |
| P9 | 규칙으로 확인 가능한 지표와 정답 설정(오라클) 기준선으로 평가한다. | **[논문]** LightRAG의 우위는 정답 없는 LLM 판정 결과였다. HippoRAG 2의 독립 재실행(다른 데이터·설정, 정답 있는 질의응답)에서는 평균 6.6 F1로 dense 검색의 57.0보다 낮았다. Zep, Mem0: 작은 규모에서 전체 문맥 기준선이 강하다. |
| P10 | 보인 것만 주장한다. | 지식그래프가 말투, 한국어 높임, 호칭을 개선한다고 보인 논문은 찾지 못했다. |

## 3. 그래프 모델 (무엇을 저장하는가)

논리적으로는 (나, 상대)를 중심으로 한 하나의 그래프입니다. 물리적으로는 두 곳에서 옵니다. 말투 부분은 PostgreSQL의 메시지에서 규칙으로 계산하고, 사건·관계 부분은 지금의 Graphiti/Neo4j에 그대로 있습니다. 필수 범위에서 `backend/app/graph/schema.py`는 바꾸지 않고 재추출도 하지 않습니다.

### 3.1 말투 관찰 (규칙 계산, 필수)

사용자가 상대에게 보낸 메시지마다 모델 호출 없이 계산합니다.

- **문장별 어미 분류:** `합쇼체 / 해요체 / 해체 / 알 수 없음`. 서술어 어미가 없는 줄(넵, ㅇㅋ, "내일 10시 회의실 B", "확인 완료", "별일 아님")은 `알 수 없음`이며 집계에서 뺍니다.
- **메시지 라벨:** 먼저 반말/존댓말을 가릅니다. 분류된 문장에서 존댓말(합쇼체+해요체)도 반말도 70%에 못 미치면 `혼용`입니다. 존댓말이면 그 안에서 문장이 많은 단계(같으면 합쇼체)입니다. 합쇼체와 해요체가 섞인 메시지는 혼용이 아닙니다 — 혼용으로 빼면 존댓말로 바꾼 뒤의 메시지가 구간에서 빠져 예전 반말이 "지금 말투"로 남습니다(구현 리뷰 2026-11-16). '요'가 빠진 연결 어미는 뒤에 종결 어미가 읽히는 문장이 없을 때만 반말로 셉니다. **[판단]**
- **호칭:** 메시지에 나온 문자열 그대로 저장합니다(LLM의 바꿔 쓰기를 쓰지 않으므로 팀장/팀장님 뒤바뀜이 없습니다). 문장 첫머리(줄의 처음, 대답·감탄사 뒤, 마침표 뒤)에 있고 쉼표·호격으로 표시되며 격조사가 붙지 않은 경우만 호칭으로 봅니다. 님 없는 직함('이사', '책임')은 상대 별칭에 있거나 별칭의 이름이 붙었을 때만, 호칭 꼴의 나열("부장님, 차장님 모두")은 뺍니다. **[판단]** 실제 대화에서 통하는지는 미확인입니다.
- **기타(나중에):** 이모지 수, ㅋㅋ/ㅠㅠ 수, 글자 수, 1:1/단체방. 어떤 슬롯도 움직이지 않으므로 필수 범위에서 구현하지 않았습니다.

기존 `ai/style_suggest.py`의 `_ending`은 그대로 쓸 수 없습니다. 마지막 줄의 끝 어미만 보고, `알 수 없음`이 없으며, -니다/-요/-죠가 아닌 것을 모두 반말로 처리합니다. 문장 단위 분류기는 새로 작성합니다(테스트 포함 약 2일).

### 3.2 말투 프로필 (규칙 계산, 필수)

`(사용자, 상대, as_of)`를 받는 순수 함수입니다. 새 패키지를 만들지 않고 `ai/style_suggest.py`를 변화 시점 구간 나누기와 `as_of`로 확장합니다. 화면에는 `(나)-[:REGISTER]->(상대)` 간선처럼 표시합니다.

- **슬롯:** `speech_level`과 `address_term`. 각각 `{값, 시작, 끝, 관찰 수, 단계별 건수, 근거 메시지 id, 상태}` 구간의 목록입니다.
- **구간 규칙(전부 [판단]):**
  - 새 말투 구간은 **연속 2개 메시지가 반말/존댓말의 같은 쪽으로 일치**하면 `확정`입니다(합쇼체와 해요체는 같은 쪽 — 구간 값은 그 연속의 다수 단계, 같으면 합쇼체). 메시지 1개나 `알 수 없음`으로는 구간을 열지 않습니다.
  - 현재 구간의 메시지가 최근 6건(알 수 없음 제외)에 하나도 없으면 `확정`이 아니라 `후보`로 낮춥니다(옛 구간을 "최근 n건"이라고 말하지 않게).
  - "확정"과 "표시 가능"의 기준은 같습니다. 초안의 "3건 이상이어야 표시"는 없앱니다. 대신 건수를 항상 표시해("최근 2건") 근거가 얇다는 것을 사용자와 모델이 보게 합니다.
  - 호칭은 2회 이상이면 `확정`입니다(연달아 쓰지 않아도 됩니다). 1회뿐이면 `후보`이고 제안에 "1회 관찰"로 표시합니다. 확정된 호칭 뒤에 한 번 나온 다른 호칭은 확정된 호칭을 밀어내지 않고 따로 후보로 둡니다 — 위계 힌트·상태 블록·경고는 확정된 호칭만 봅니다.
  - 총 메시지 수 문턱은 없습니다(구현 초기의 "내 메시지 5건 미만이면 제안 없음"은 리뷰에서 없앴습니다).
  - K=1/2/3에 대한 민감도를 보고합니다(`evals/suggestion_accuracy.py --segment-k`).
- **상황별 말투(두 값 상태):** 변화 시점 이후 최근 6개 메시지에 두 단계가 섞여 있으면 하나의 현재 값으로 합치지 않고 "합쇼체 n건 / 반말 m건"으로 내보냅니다. 이 경우 제안은 값을 정해 주지 않고 사용자에게 묻습니다.
- **위계 힌트:** 호칭의 직함 사전(파트장님/교수님/선배 → 상대가 윗사람)에서 얻습니다.
- **연락 빈도(나중에, 미구현):** 설명용으로만 보여 주고 어떤 슬롯도 움직이지 않습니다. Peterson 2011(영어 회사 이메일)에서 비격식 비율은 발신량 약 50통 이상에서만 올랐고 1~10통과 11~50통은 차이가 없었습니다. 우리 데이터 규모에서는 친밀도의 근거가 못 됩니다.
- **시간:** 메시지의 `sent_at`만 씁니다. `as_of`는 구간을 나누기 전에 관찰을 걸러냅니다.
- **단체방(나중에, 미구현):** 다른 것이 없을 때만 기준선에 넣습니다. 지금은 대화방에 종류 표시가 없어 상대의 모든 대화방을 합칩니다. 단체방을 실제로 가져오기 시작하면 대화방에 종류를 두고 1:1을 우선합니다.

**c3(이서연)의 예.** 아래는 비평이 `data/synthetic/sample_conversations.json`에서 보고한 값입니다. 구현 전에 손으로 다시 계산해 확인합니다.

| 구간 | 값 | 근거 | 상태 |
|---|---|---|---|
| 말투 1 | 반말 | c3:m02, m04, m06 (3건) | 이전 |
| 말투 2 | 합쇼체 | c3:m08, m10 (2건) | 확정 (연속 2건) |
| 호칭 | '서연 파트장님' | c3:m08 (1회) | 후보 |

이 상대는 "시점에 따라 바뀐 말투"가 아니라 "상황에 따라 다른 말투"일 가능성이 큽니다. c3:m06~m07에서 두 사람이 "회사에선 존댓말 써야겠네", "공식 자리에선 그게 낫겠다, 사적으로는 편하게 하자"고 합의했고 `evals/characters.csv`에도 같은 내용이 있습니다. 변화 이후 메시지가 합쇼체 2건뿐이라 두 값 규칙은 발동하지 않습니다. 그래서 3.3의 그래프 조회가 이 합의를 제안의 근거로 보여 줘야 합니다.

**계산 방식.** 읽을 때 계산하고 테이블을 만들지 않습니다. `as_of`, 삭제, 순서가 뒤바뀐 입력이 구조상 저절로 맞고 마이그레이션이 없습니다. 비용은 수십~수백 행에 대한 정규식입니다. 캐시 테이블과 Neo4j에 프로필을 저장하는 것은 **나중에**입니다.

### 3.3 변화의 이유와 범위 (그래프 조회, 필수)

규칙이 못 하고 그래프만 할 수 있는 일입니다. 무효화나 불안정한 속성에 기대지 않고, 재추출도 필요 없습니다.

- 규칙 프로필이 날짜 T에서 변화 시점을 찾으면, 상대 노드 이웃의 `Event` 노드 중 에피소드 시각이 T 전후 약 7일 안인 것을 조회합니다. 기존 이웃 조회 호출을 그대로 씁니다.
- 찾은 사건을 제안에 **계기**로 붙입니다(예: c3:m05 "파트장으로 발령").
- 같은 조회로 그 기간의 관계 사실 원문을 **범위 단서**로 보여 줍니다(예: c3:m06, m07의 합의).
- 이 정보는 사용자에게 보여 주는 제안의 근거일 뿐이고 첨삭 프롬프트에 내용으로 들어가지 않습니다.
- 측정: 변화 시점 사례마다 "계기 사건이 맞는가(예/아니오)"를 사람이 판정합니다.
- ±7일은 **[판단]** 입니다.

### 3.4 사건과 관계 (기존 유지)

- `Event`, `Involved`: 변경 없이 경고에 씁니다. `Event.status`를 읽기 시작하는 것은 **권장**입니다.
- `Relationship`의 `speech_style`, `address_term`, `closeness`: 새 경로에서는 읽지 않습니다. 필수 범위에서는 스키마에 남겨 둡니다. 현행 `persona_signals`와 비교하려면 필요하기 때문입니다.
- `closeness`는 안정적으로 추출된다는 근거가 없어 장기적으로 사용자가 직접 정하는 값으로 둡니다.
- `Relationship`을 `RelationTie`와 `Interaction`으로 나누는 스키마 분리와 재추출은 **나중에**입니다. 3.3의 조회에서 "점심 물어봄" 같은 비관계 사실이 실제로 방해가 된다고 확인될 때만 합니다. 닫힌 enum에 맞지 않으면 버리는 방식은 우리 선택입니다. EDC는 영어 백과 문장에서 추출 후 스키마로 정규화하면 중복 관계명이 줄어든다는 것을 보였을 뿐, 같은 방법을 시험한 것은 아닙니다.

## 4. 만들고 유지하는 방법

1. **가져오기(변경 없음).** 메시지와 문체 조각을 저장합니다.
2. **말투 계산(필수).** 수집 단계가 없고 필요할 때 메시지에서 계산합니다. 결정론적이라 실행 간 일치율은 구조상 100%이며, 데이터가 기기 밖으로 나가지 않습니다.
3. **Graphiti 수집(변경 없음).** 기존 스키마 그대로입니다. 새 변화 시점 대화가 추가되면 그것만 수집합니다(메시지당 10~15초).
4. **무효화 노이즈(권장, 측정 후 결정).** `retriever.py:143`의 `invalid_at` 필터를 통째로 없애지 않습니다. 26개 중 15개는 1시간 내 부산물이 아니었고, 필터를 없애면 바뀐 회의 날짜 같은 실제로 대체된 사실이 돌아와 거짓 경고를 낼 수 있습니다. 순서는 다음과 같습니다.
   - 먼저 `eval_cases.csv`의 사건 사례에 `expected_context`와 기대 경고를 채웁니다. 지금은 5건 모두 비어 있어 차이를 감지할 수 없습니다.
   - 세 설정을 `warning_hit`와 거짓 경고 수로 비교합니다: (가) 전부 신뢰, (나) 부산물로 보이는 것만 무시(`invalid_at`이 `valid_at`에서 1시간 이내이거나, 무효화한 에피소드가 같은 대화·같은 날), (다) 전부 무시.
   - 결과가 나온 뒤에 기본값을 정하고 검색 버전 문자열을 올립니다.
5. **추출 불일치(권장).** 안정성 표는 36개 메시지 세트에서만, 살아남는 속성(`relation_type`, `hierarchy`, `Event`의 type/status)에 대해 만듭니다. 이미 있는 독립 그래프 2개가 남아 있으면 3회 중 2회로 씁니다. 재추출 후 투표하는 방식은 만들지 않습니다(8절).
6. **삭제.** 파생 데이터를 저장하지 않으므로 대화를 지우면 프로필에 흔적이 남지 않습니다. 승인된 설정은 사용자의 설정으로 남습니다.
7. **검증기 버전(필수).** `RewriteResult`와 평가 CSV에 `validator_version` 문자열을 추가합니다. 직함 사전을 고치면(5절) 모든 조건의 사실 추출이 바뀌므로, 그 뒤에 C와 D0을 한 번 다시 돌리고 11/16 수치는 재사용하지 않습니다.

## 5. 첨삭할 때 읽는 방법 (문장에 닿는 경로)

첨삭 시점에 모델 호출을 추가하지 않습니다. 프로필 계산이 실패하면 요청은 C와 똑같이 동작합니다.

### 5.1 경로 S: 설정 제안 (필수, 주 경로)

실측에서 문장을 바꾼 유일한 경로입니다. 규칙 프로필이 만들고 그래프가 이유를 붙이며 사용자가 승인합니다. 자동 저장은 없습니다.

- **새 설정 항목 `speech_level`은 만들지 않습니다.** 프로필의 말투 단계를 기존 격식 1~5에 대응시킵니다: 반말 → 1~2, 해요체 → 3, 합쇼체 → 4~5. `style_suggest._formality`와 `persona_signals`가 이미 3을 '-요'체, 4 이상을 '-습니다'체로 취급하고, 격식 3→4만으로 "죄송합니다"가 3/3 나왔습니다. 설정 화면 작업, 우선순위 규칙, 요청별 조정 버튼(`apply_adjust`) 충돌이 모두 생기지 않습니다.
- **호칭**은 승인돼야만 설정에 들어갑니다. 1회만 관찰된 호칭은 "1회 관찰"로 표시합니다.
- **상황별 말투로 보이면 값을 정해 주지 않고 묻습니다.** 두 값 상태이거나, 그래프가 범위 합의를 찾았거나, 변화 후 관찰이 2건뿐인 경우입니다.

c3의 제안 카드 예(3.2 표의 값 기준, 손계산 후 확정):

```
이서연 님에게 쓰는 말투가 바뀐 것으로 보입니다.
말투: 반말(3건: c3:m02, m04, m06) → 합쇼체(최근 2건: c3:m08, m10)
호칭: '서연 파트장님' (1회 관찰: c3:m08)
계기(그래프): 파트장 발령 (c3:m05)
범위 단서(그래프): "회사에선 존댓말 써야겠네"(c3:m06) / "사적으로는 편하게 하자"(c3:m07)
→ 공식 자리에서만 쓰는 말투일 수 있습니다. 어떻게 할까요?
  [격식 4 + 호칭 추가]  [그대로 두기]
```

한계: 지금 설정은 상대당 하나입니다. "격식 4"를 승인하면 사적인 초안에도 적용되고, 그때는 사용자가 요청별 조정(more_casual)을 써야 합니다. 상황별로 설정을 나누는 것은 **나중에**입니다. 승인 시 `notes`에 "공식 자리에서만 존댓말"을 함께 적는 선택지도 가능하지만 효과는 측정되지 않았습니다. **[판단]**

승인은 기존 `PUT /persona`로 합니다. 제안 함수에 `as_of` 인자를 추가합니다(평가용).

### 5.2 경로 W: 경고 (권장)

저장된 설정이 있으면 관찰된 상태는 문장을 바꾸지 않습니다. 대신 코드가 경고 두 가지를 만듭니다: "관찰된 호칭이 설정에 없음", "설정과 최근 말투 불일치". 사건·날짜 경고는 기존 유사도 경로에 그대로 둡니다(한 건에서 recall 0.50 → 1.00).

### 5.3 경로 B: 상태 블록 (권장, 설정이 없는 상대에게만)

초안의 "설정이 침묵할 때만 블록이 어미를 조정한다"는 성립하지 않습니다. 격식은 기본값 3인 필수 항목이라 설정이 말투에 대해 침묵하는 일이 없고, 사용자가 고친 값과 손대지 않은 기본값을 구분할 표시도 없습니다. 그래서 다음과 같이 좁힙니다.

- 블록은 **저장된 설정이 없는 경우(`auto` 경로)** 에만 말투를 조정할 수 있습니다. 이 경로의 프롬프트는 이미 "문체 예시가 있으면 그 말투를 따른다"고 되어 있습니다.
- 설정이 있으면 5.1의 제안과 5.2의 경고만 나가고 문장은 바뀌지 않습니다. "명시적 설정이 이긴다"(`docs/design.md:93`, system.md 규칙 5)를 그대로 지킵니다.
- 블록에는 확정된 값과 건수만 넣습니다. 관찰된 호칭과 날짜가 붙은 상충 사실은 넣지 않습니다.

```
[관계 상태 — 내 과거 메시지에서 관찰, 내용 근거 아님]
말투: 합쇼체 (최근 2건)
상하: 상대가 윗사람 (호칭 직함 기준)
```

- 이 블록과 함께 `prompts/rewrite-v4/system.md`에 "격식 1~2 = 반말, 3 = 해요체, 4~5 = 합쇼체 위주"를 명시합니다.
- 첫 결과(제안 정확도)가 좋을 때만 만듭니다.

### 5.4 경로 X: 예시 걸러내기 (권장)

kNN 후보를 현재 말투 구간의 발화로 제한합니다. 2개 미만이 남으면 제한 없는 후보로 돌아갑니다. 이것은 **[판단]** 이고 논문 근거가 없습니다. Wang 2025는 주제가 비슷한 예시 선택이 도움이 되지 않았다고 보고했을 뿐, 시점·구간 기준 선택은 시험하지 않았습니다. `search_episodes`에 `after` 경계를 세 구현(`repositories/base.py`, `memory.py`, `postgres_conversations.py`)에 추가해야 하므로 상태 블록 다음 순서입니다.

### 5.5 검증기

- **필수: 직함 사전 공유.** `preserve.py`가 파트장/센터장/매니저를 사람 이름이 아니라 직함으로 보게 합니다. `validator_version`과 함께 첫 기준선 실행 전에 넣습니다.
- **권장: 말투 사후 점검.** 기본값은 꺼짐이고 분류기 정확도 수치가 나온 뒤에만 켭니다.
  - **반말/존댓말 경계만** 강제합니다. 합쇼체와 해요체의 비율은 보고 지표와 경고일 뿐, 재생성 조건이 아닙니다. 자연스러운 공손한 한국어는 둘을 섞어 씁니다.
  - 기준은 `persona_used.formality`, 즉 `apply_adjust` 적용 후의 격식이 뜻하는 단계입니다.
  - 재생성을 쓴다면 1차 결과를 `WorkflowState`에 보관합니다. 2차가 사실 검증에 실패하면 1차를 경고와 함께 추천합니다. 지금 구조(`MAX_REGENERATIONS`=1, 최신 결과만 보관)로는 말투만 어긋난 멀쩡한 1차가 원문 복귀로 바뀔 수 있습니다. 이 순서에 대한 테스트를 추가합니다.
- **권장: 호칭 누출 표시.** 초안에도 설정에도 없는 직함·호격이 출력에 있으면 표시합니다.

## 6. 실험 조건과 평가

### 6.1 주 결과: 제안 정확도 (생성 없음)

초안의 "D2 대 C" 비교는 주 결과로 쓰지 않습니다. 평가 하네스에서 C의 이서연 설정은 `'colleague'`가 `ADDRESS_FROM_ALIASES`에 없어서(`services/synthetic_loader.py:40`) 동료 기본값(격식 3, 호칭 없음)일 뿐이고, `characters.csv`에는 이미 '서연 파트장님'이 별칭으로 있습니다. 그 비교는 "맞는 설정이 낡은 설정을 이긴다"만 보여 주는데, 이는 조건 B가 이미 보인 것입니다. 또 같은 규칙 분류기가 제안을 쓰고 채점도 합니다.

대신 각 (상대, `as_of`)에서 제안된 {말투 단계, 호칭, 시작일}을 **사람이 쓴 정답 설정 타임라인**과 비교합니다. (상대, `as_of`)마다 데이터 한 점이 나오므로 표본이 더 많습니다.

| 비교 대상 | 설명 |
|---|---|
| 규칙 프로필 | 이 설계(3.2) |
| 그래프 신호 | 현행 `graph/persona_signals.py` |
| 전체 기간 요약 | 현행 `ai/style_suggest.py` (변화 시점 없음) |

- 세 출처를 공정하게 비교하려고 공통 세밀도(반말/존댓말, 호칭, 변화 날짜)로 채점합니다. 해요체/합쇼체 구분은 규칙 프로필에 대해서만 따로 보고합니다.
- 변화 시점 사례에서는 "계기 사건이 맞는가"(3.3)도 함께 보고합니다. 이것이 그래프가 더해 주는 것을 보여 주는 지표입니다.
- 제안 정밀도(제안 중 정답과 맞는 비율)를 공개합니다.

### 6.2 첨삭 비교 (2차 결과)

새 `Condition` 값을 만들지 않습니다. `run_eval.py`의 `--apply-suggestion`, `--persona-override` 플래그로 C의 설정만 바꿉니다.

| 조건 | 정의 | 목적 |
|---|---|---|
| C | 설정 + kNN 예시 4개 | 기준선 |
| C + 정답 설정 | C에 사람이 쓴 정답 설정 적용 | 상한(오라클) |
| C + 제안 | C에 규칙 제안 적용. (가) 전부 적용, (나) 정답과 맞는 제안만 적용, 두 형태로 보고 | 제품 경로 |
| D0 | 현행 graph-context-v3 | 연속성 |

- "C + 제안"은 오라클과 같아질 수는 있어도 넘을 수는 없습니다. 주장은 "제안이 수동 관리 없이 오라클에 도달한다"입니다.
- 규모는 4개 조건 × 약 25건 × 3회로 약 300회 호출입니다.
- 권장 항목을 만들 경우 추가하는 조건(이 순서로): 상태 블록(설정 없는 사례만, 실험으로 표시) → 예시 걸러내기 → C-render(빈 슬롯 블록, 배치 대조군) → C-full(이 상대와의 전체 메시지). C-full은 `fit_examples`의 2,400자 제한을 우회해야 합니다.

### 6.3 사례

- **목표:** 8명 이상의 상대에 걸쳐 20~30건. 실행 전에 팀원이 작성합니다. 각 사례에 정답 말투 단계, 정답 호칭, 필요 태그, `expected_context`를 붙입니다.
- **변화 시점 상대를 6명 이상 새로 요청합니다(1주차 말까지).** 방향을 다양하게 합니다: 반말→존댓말, 존댓말→반말, 호칭만 변화, 변화 없음(음성 사례). 작성 지침은 인물 설명만 담고 K=2 같은 임계값을 언급하지 않습니다.
- **이서연에게 보내는 사적 초안 2건 이상**(10/21 이후, 정답 = 반말, 직함 없음)을 추가합니다. 이 상대에 대한 과잉 격식 점검입니다.
- **E004의 정답을 실행 전에 팀원이 확정합니다.** "예민했다"는 사과는 사적인 메시지로 볼 여지가 있어 정답 말투와 호칭이 모호합니다.
- **친한/반말 상대 층:** 과잉 격식을 점검합니다. Park 2025는 한국어 객관식 공감 과제에서 LLM이 과하게 공감하고 긴 응답을 고르며, 위계보다 친밀도에서 사람과 더 어긋남을 보였습니다. 이것이 첨삭의 과잉 격식으로 이어진다는 것은 우리 가설입니다.

### 6.4 분류기 검증

- 팀원이 손으로 라벨한 합성 문장 100~150개에 대한 정확도를 잽니다.
- **90% 미만이면 멈추지 않고 축소합니다.** 반말/존댓말 경계만 쓰고 해요체/합쇼체 구분은 보고에서 뺍니다.
- StyleKQC는 존댓말/반말 경계의 참고 확인에만 쓸 수 있습니다. 해요체/합쇼체 경계는 팀의 손 라벨로만 검증됩니다.
- 규칙은 기기 안에서 돌기 때문에, 각 팀원이 본인의 실제 대화 내보내기에 분류기를 돌려 **집계 수치만** 보고합니다(`알 수 없음` 비율, 직접 라벨한 50줄의 혼동표). 실제 문장은 기기 밖으로 나가지 않습니다.

### 6.5 첨삭 지표 (세 축을 따로 보고, Briakou 2021)

- **말투:** 정답 말투 단계 일치, 승인된 호칭의 정확성, 미승인 호칭 누출률, 반말 상대에 대한 과잉 격식률. 분류기 채점과 별도로 **표본을 사람이 라벨**합니다. 같은 분류기가 제안과 채점을 모두 하기 때문입니다.
- **내용:** 검증기 통과율과 원문 복귀율, chrF(초안, 첨삭). chrF는 한국어에서 검증되지 않았습니다.
- **사람:** 블라인드 쌍 비교, 순서 무작위, 평가자 2명, 일치도 보고(Mackraz 2026).

### 6.6 분석과 주장 범위

- 사례 안에서 반복을 평균하고, 사례별 쌍 차이를 보며, 서로 다른 상대 수를 유효 표본으로 보고합니다(Miller 2024). 전체 사례 표를 공개합니다.
- 변화 시점 상대가 6명 이상 모이면 부호 검정을 병기합니다(6명 중 6명이 같은 방향이어야 p ≈ 0.03). 큰 효과만 감지할 수 있다고 명시합니다(Card 2020).
- **1주차 말에 6명이 안 되면** 유의성 표현과 "몇 건 중 몇 건" 식의 합격 기준을 모두 빼고 사례별 기술 표만 냅니다.
- 실패로 보는 경우와 그때의 주장은 다음과 같습니다.

| 결과 | 그때 하는 말 |
|---|---|
| 규칙 프로필의 제안 정확도가 그래프 신호나 전체 기간 요약보다 낫지 않다 | P2가 이 데이터에서 성립하지 않는다. 그대로 보고한다. |
| "C + 제안"이 오라클에 못 미친다 | 제안 정밀도와 함께 격차를 보고한다. |
| 계기 사건 조회가 대부분 틀린다 | 그래프의 필수 역할이 성립하지 않는다. 그래프는 경고 용도로만 주장한다. |
| C-full이 "C + 제안"과 같다 | 주장은 "더 나은 문장"이 아니라 "유지되는 상태, 설명 가능한 제안, 낮은 비용"이 된다. |
| 제안 적용이 중립·친한 사례에서 검증 실패나 과잉 격식을 늘린다 | 해당 제안 규칙을 끈다. |

## 8. 위험, 미해결 질문, 검토하고 버린 것

**위험**

- 한국어 채팅 어미(요 탈락, ~용, -죠, 조각 문장) 때문에 많은 메시지가 `알 수 없음`이 되어 구간 규칙이 굶을 수 있습니다.
- 임계값은 전부 판단입니다. K=2는 한 번의 격식 있는 연속 대화에도 발동할 수 있습니다.
- 설정 경로의 효과는 사례 1건에 근거합니다.
- 상대당 설정이 하나라서 상황별 말투를 가진 상대에게 제안을 승인하면 사적인 초안이 과하게 격식을 띨 수 있습니다. 이서연 사적 초안 사례로 이를 직접 잽니다.
- 팀원이 가설을 알고 사례를 씁니다. 지침에서 임계값을 빼는 것으로 일부만 완화됩니다.
- 손 라벨 문장도 같은 팀원이 쓴 깨끗한 문장이라 실제 채팅에 대한 정확도는 덜 알려 줍니다. 기기 내 집계 보고로 보완합니다.
- 말투의 핵심 계산이 Neo4j 밖에 있습니다. "그래프는 어디 있느냐"는 질문에는 이렇게 답합니다: 그래프 모양의 모델이고, 말투 간선은 규칙으로 만들며, Graphiti 그래프는 계기와 범위를 찾는다. 그래프의 기여는 "계기 사건 정확도"와 "규칙만 대 규칙 + 그래프 근거"로 보여 줍니다.

**미해결 질문**

- 호격과 지칭을 가르는 규칙이 실제 대화에서 통하는가.
- 설정이 없는 상대에게 상태 블록이 실제로 문장을 움직이는가.
- 블록을 키-값으로 쓸지 문장으로 쓸지. LongMemEval은 오라클 검색 조건의 질의응답에서 읽기 전략에 따라 최대 약 10점 차이를 보고했으나(Chain-of-Note + JSON이 최고, JSON만으로는 일관되게 낫지 않음), 말투 블록에 대한 효과 크기를 뜻하지는 않습니다. 싸게 한 번 시험할 가치만 있습니다.
- 계기 조회의 ±7일 창이 적절한가.
- 1회 관찰된 호칭을 제안에 포함하는 것이 사용자에게 도움이 되는가(제안 정밀도로 판단).

**검토하고 버린 것**

| 버린 것 | 이유 |
|---|---|
| 새 설정 항목 `speech_level` | 격식 대응으로 같은 효과. 조정 버튼과 충돌하고 설정 화면·우선순위 작업이 필요. |
| 저장된 설정이 있을 때 관찰 상태로 문장 조정 | "명시적 설정이 이긴다"를 깬다. 격식에는 "침묵"이 없다. |
| 커뮤니티 탐지, 전역 검색 | 근거가 약 100만 토큰 규모 말뭉치다. |
| Personalized PageRank | 기준점(상대)을 알고 있고 사실이 1홉 거리다. |
| 검색 시점 LLM 필터 | 모델 호출 없음 속성을 깬다. |
| 세밀한 이중 시간 원장 | Jiang 2026(초록)에서 표시 형식을 맞추면 이득이 거의 0이었다. |
| 문체 임베딩 | 확인된 한국어 모델이 없다. e5는 주제를 담는다(Wegmann 2022). |
| 상대의 말투 따라 하기, LLM이 추론한 친밀도 | 뒷받침하는 근거가 없다. |
| 재추출 후 투표 | 비용이 크고, Self-Consistency는 추론 과제에서만 보였다. |
| 연락 빈도를 친밀도 대용으로 사용 | Peterson 2011에서 약 50통 미만은 차이가 없었다. |
| `invalid_at` 필터 전면 제거 | 측정 없이 오류 하나를 다른 오류로 바꾼다. 세 설정 비교 후 결정. |

## 9. 검증에서 나온 지적과 반영 내용

두 비평(실현 가능성, 근거)의 지적과 처리입니다.

**치명적 지적 4건(모두 설계 변경)**

| 지적 | 반영 |
|---|---|
| "3건 이상이면 표시" 임계값이 유일한 그래프 필요 사례(c3, 변화 후 2건)에서 블록을 꺼 버린다. 초안의 예시도 데이터와 다르다. | 확정과 표시 기준을 "연속 2건 일치"로 통일하고 건수를 표시한다. 예시를 c3 데이터 기준으로 다시 썼다(이전 = 반말 3건, 현재 = 합쇼체 2건, 호칭 1회). 구현 전에 손계산한다. |
| 이서연의 말투는 시점 구간이 아니라 상황별이다. | 두 값 상태를 추가했다. 제안은 값을 정하지 않고 묻는다. 그래프가 범위 합의를 근거로 보여 준다. 사적 초안 사례 2건을 추가하고 E004 정답을 실행 전에 확정한다. 상대당 설정이 하나라는 한계는 위험으로 남겼다. |
| D2 대 C는 혼입되어 있고 순환적이다. | 주 결과를 생성 없는 제안 정확도(세 출처 비교)로 바꿨다. 오라클 조건을 추가했다. 말투는 표본을 사람이 라벨한다. |
| 필수 범위에 그래프 작업이 없다. | 변화 시점의 계기 사건과 범위 단서 조회를 필수로 넣었다(재추출 없음, 사례별 정오 측정). |

**주요 지적**

| 지적 | 반영 |
|---|---|
| 설정은 말투에 대해 침묵하지 않는다. | 상태 블록은 설정이 없는 경우에만 쓴다. 설정이 있으면 경고와 제안만 낸다. D1은 실험으로만 둔다. |
| `speech_level` 항목이 조정 버튼을 무력화한다. | 항목을 만들지 않고 격식에 대응시킨다. |
| 말투 사후 점검이 멀쩡한 첨삭을 원문 복귀로 만든다. | 반말/존댓말 경계만 강제한다. 1차 결과를 보관한다. 기본 꺼짐, 권장으로 내렸다. |
| 계획한 데이터로는 통계 기준을 못 맞춘다. | 변화 시점 상대 6명 이상을 요청한다. 못 모이면 유의성 표현을 뺀다. 주 결과는 제안 정확도다. |
| 1~3주 범위가 과하다. | 2주짜리 뼈대(제안 확장, 평가 플래그, 직함 사전, 그래프 조회)와 4개 조건으로 줄였다. 나머지는 결과를 본 뒤 순서대로 한다. |
| `_ending` 재사용은 불가능하고 90% 중단 규칙에 대안이 없다. | 문장 단위 분류기를 새로 작성한다(약 2일). `알 수 없음`을 둔다. 90% 미만이면 경계만 쓰도록 축소한다. 실제 대화는 기기 내 집계만 보고한다. |
| `invalid_at` 필터 제거가 측정 없는 교체다. | 부산물만 무시하는 안을 포함한 세 설정을 비교한 뒤 결정한다. 권장으로 내렸다. |
| MemoryAgentBench "모든 시스템 ≤56%"는 틀렸다. | 문구를 고쳤다. 판별 수치 차이를 명시하고 간접 근거로만 쓴다. 직접 근거는 우리의 11/26이다. |
| P1의 "모두 키로 읽는다"는 과장이다. | "id로 읽기는 우리 선택"으로 고쳤다. |
| P2의 Danescu·Atil 인용이 과하다. | 범위를 명시했다. 한국어 규칙의 정확도는 미증명이라고 적었다. |
| 연락 빈도와 Peterson. | 설명용으로만 쓰고 어떤 슬롯도 움직이지 않는다. |
| P5와 예시 걸러내기에 근거가 없다. | 걸러내기를 판단으로 표시하고 필수에서 권장으로 내렸다. |

**가벼운 지적**

- 직함 사전 변경으로 비교가 끊기는 문제: `validator_version`을 추가하고 C/D0을 재실행한다.
- 안정성 표 비용: 36개 메시지와 살아남는 속성으로 제한하고 기존 그래프 2개를 재사용한다. 스키마 분리는 나중에.
- P6의 오독: 1절과 P6을 고쳤다. 채점은 공통 세밀도로 한다.
- "승인된 것처럼 적용"의 과대평가: 두 형태로 보고하고 제안 정밀도를 공개한다.
- Jiang, LoCar, Park, LongMemEval 형식, LightRAG, "문헌이 예측", EDC, StyleKQC: 모두 비평의 범위대로 문구를 좁혔다.

**고치지 않고 남긴 것**

- 임계값(K=2, 70%, 최근 6건, ±7일)은 여전히 판단입니다. 민감도 보고로만 다룹니다.
- 설정 경로의 효과는 아직 1건 근거입니다. 이번 평가가 그것을 넓히는 작업입니다.
- 팀원이 가설을 알고 사례를 쓴다는 점은 완전히 해결되지 않았습니다.
- 지식그래프가 말투를 개선한다는 논문 근거는 여전히 없습니다. 이 문서는 그렇게 주장하지 않습니다.
