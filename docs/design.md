## 0. v2 정정 내역

v2는 이 서비스를 "AI 페르소나가 답장을 생성하는 시스템"으로 잘못 이해하고 썼다. 실제 서비스는 **사용자 본인의 초안을 상대별 말투로 첨삭**한다.

| 항목 | v2 (잘못됨) | v3 (팀 설계 기준) |
|---|---|---|
| 서비스 | 페르소나가 메시지에 답장 | 사용자 초안을 상대·상황에 맞게 **첨삭** |
| 멀티페르소나 | 여러 AI 캐릭터 | **한 사용자의 상대별 말투 설정** (팀장용, 동생용 …) |
| 페르소나 생성 | LLM이 성격·말투를 생성 | **사용자가 직접 설정**, 버전 관리. 대화에서 성격을 추정하지 않음 |
| 핵심 실패 | 페르소나 모순 | **원문 사실 변경** (날짜·수량·가능 여부·약속·거절 의도) |
| 검수 | CoVe + NLI + 루브릭, 재시도 2회 | **보존 항목 규칙 대조** + 스타일 루브릭, **재생성 최대 1회**, 재실패 시 원문 유지 |
| 저장소 | 처음부터 Neo4j | **PostgreSQL + pgvector 기본**, Neo4j는 D 실험 |
| 관점 분리 (`group_id`) | 페르소나별 관점 | **사용자 격리** 단위 (`user:{user_id}`) |
| 출력 | 최종 응답 자동 출력 | **추천 표시 → 사용자가 적용·수정·취소**, 자동 전송 없음 |
| 평가 | 메모리 QA 중심 | **A/B/C/D 비교 실험**, 사실 보존 98% 목표 |

v2에서 유지하는 것: Graphiti(Zep) 기반 시간 지식 그래프 설계, 커스텀 타입, 하이브리드 검색·재정렬 아이디어. 모두 **D 실험 경로**로 옮겼다.

## 1. 서비스 한 줄 정의

**상대와 상황에 맞는 사용자의 말투를 적용하되, 원문의 사실과 의도를 보존하는 메시지 첨삭 서비스.** (project-design §1)

예: 원문 "오늘 정리해서 내일 오전까지 보내드릴게요." → 팀장에게는 격식 있게, 동기에게는 편하게 바꾼다. 하지만 "내일 오후"로 바꾸거나 과거 대화의 사유를 끼워 넣으면 **실패**다.

## 2. 전체 흐름

```
① 관계별 페르소나 (사용자 설정)
   상대 등록 → 격식·친근함·직접성·길이·이모지·선호/금지 표현 설정 → persona_versions

② 대화 가져오기 (비동기 작업)
   업로드 → 파싱·화자 지정 → 비식별화·중복 제거
     ├─ C 경로 (기본): 2~6턴 묶음 → 임베딩 → episodes (pgvector)
     └─ D 경로 (실험): Graphiti add_episode() → 시간 지식 그래프 (Neo4j)

③ 첨삭 요청 (고정 워크플로)
   상대 선택 + 초안 + 상황
   → 의도·보존 항목 추출 (날짜·수량·사람·가능/불가·약속·조건)
   → 컨텍스트 검색 (동일 사용자·동일 상대, 요청 이전 데이터만)
        · 현재 페르소나 버전                         [A~D 공통, B부터]
        · 문체 예시: 같은 상대에게 쓴 본인 발화 kNN   [C부터]
        · 사실 맥락: 사건·관계 그래프 검색 + 재정렬   [D만]
   → 프롬프트 조립 (역할 경계 명시) → LLM 첨삭 (구조화 출력)
   → 검증 → 통과: 추천 표시 → 사용자 적용·수정·취소 → 피드백 (동의 시)
            실패: 위반 항목 전달 → 재생성 1회 → 재실패·장애: 원문 유지

⑤ 평가: A 일반 첨삭 / B +페르소나 / C +본인 과거 표현 / D +그래프
```

## 3. 근거 논문 매핑

팀 문헌 검토(P1~P15)는 그대로 따른다. 아래는 **D 실험과 워크플로 세부**에 추가로 참고하는 논문이다.

| 적용 위치 | 근거 | 가져오는 것 | 팀 문서와의 관계 |
|---|---|---|---|
| 비교 실험 구조 | LaMP (P1) | 검색 없는 기준선, 검색 방식 비교 | 팀 채택 |
| 맥락/문체 분리 | WeStar (P8), LongMemEval (P6) | `purpose=context\|style` 구분, 시점·출처 저장 | 팀 채택 |
| 설명 가능한 스타일 설정 | Style-Eliciting Prompts (P7), Drift (P9) | 수정 가능한 상대별 속성 | 팀 채택 |
| 문체 예시 선택 | **KATE** (Liu et al., 2022) | 현재 초안·상황과 가까운 예시를 kNN으로 선택 | C 경로 보완 |
| 그래프 구조 (D) | **Zep** (Rasmussen et al., 2025) | Episode/Entity/Community 3계층, bi-temporal 엣지, 엔티티 해소, 모순 엣지 무효화 | P4·P5 후속 실험 구체화 |
| 그래프 검색 (D) | **HippoRAG** (Gutiérrez et al., 2024) | 질의 인물 중심 그래프 탐색 | D 실험 |
| 재정렬 (D) | **Generative Agents** (Park et al., 2023) | 최근성·중요도·관련성 점수 | D 실험 |
| 재생성 | **Self-Refine** (Madaan et al., 2023) | 위반 항목 피드백 → 재생성 | 팀 설계의 "1회 재생성"에 적용 |
| 스타일 루브릭 | **G-Eval** (Liu et al., 2023), **LLM-as-a-Judge** (Zheng et al., 2023) | 항목별 채점, judge 편향 인지 | 팀 평가표 보조 |
| 평가 다차원화 | TST 평가 (P10), BERTScore (P11) | 보존/적합성/문체/자연스러움/수정 부담 분리 | 팀 채택 |
| 제외 | PersonaAgent의 커뮤니티 검색 (P4) | 다른 사용자 대화 검색 | **팀 제외 결정 유지** |

> v2에 있던 CoVe·DNLI·RoleLLM·Character-LLM·AutoGen은 "AI 캐릭터 답장" 전제에서 넣은 것이라 v3에서 뺐다. 추가 논문 정보는 기억에 기반하므로 인용 전에 원문을 확인한다.

## 4. 컴포넌트 설계

### ① 관계별 페르소나

팀 설계 §5.2 그대로 따른다. 이 문서에서 덧붙이는 점은 다음과 같다.

- 우선순위 (literature-review §5.2): **이번 요청에 명시한 조건 → 현재 상대별 설정 → 같은 상대의 승인된 예시 → 일반 표현**
- 명시 설정과 과거 말투가 충돌하면 **명시 설정이 이긴다**. 그래서 D 경로 그래프에서 추출한 `speech_style`은 **참고 정보**일 뿐 설정을 덮어쓰지 않는다. 다만 설정 화면에서 "과거 대화에서는 반말을 쓰셨어요" 같은 제안으로 쓸 수 있다 (사용자 승인 후 반영).

### ② 대화 가져오기

**C 경로 (기본)**: 팀 설계 §5.1 그대로. 2~6턴 묶음, 본인 발화만 문체 예시, 임베딩 모델·버전 기록.

**D 경로 (실험)**: 같은 비식별화 결과를 Graphiti에 넣는다. 구현과 검증은 [graphiti-p0 스파이크](projects/persona-ize/spikes/graphiti-p0/README.md)에서 시작했다.

| Graphiti 단계 | 동작 | 이 서비스에서의 의미 |
|---|---|---|
| 엔티티 추출 | Person·Event 추출 | 상대·제3자·사건 식별 |
| 엔티티 해소 | 후보 검색 → LLM 동일 판정 | "박지현" = "지현 팀장님" = "팀장님" |
| 사실·시간 추출 | 엣지 + `valid_at` | "10/5 일정 충돌", "11/5까지 자료 약속" |
| 모순 무효화 | 옛 엣지에 `invalid_at` | 동기 → 파트장, 반말 → 존댓말 변화 이력 |

커스텀 타입은 [p0/schema.py](projects/persona-ize/spikes/graphiti-p0/p0/schema.py)에 있다: `Person(role)`, `Event(event_type, status, importance)`, `Relationship(relation_type, speech_style, address_term, closeness)`, `Involved(participant_role, feeling)`.

**격리 규칙 (팀 설계 §5.4 반영)**
- `group_id = "user:{user_id}"` — 사용자 단위로 그래프를 분리한다. 다른 사용자 그래프는 검색하지 않는다.
- 상대 범위는 검색 시 `center_node_uuid=상대 노드`와 서버 쿼리 템플릿으로 제한한다. **LLM이 만든 Cypher는 실행하지 않는다.** 최대 1~2홉, 결과 수 제한.
- 원문 삭제 시 해당 에피소드에서 파생된 엣지·노드도 삭제한다. Graphiti 엣지의 `episodes` 필드로 출처를 추적한다.
- 추출된 사실과 사용자가 확정한 사실은 구분한다.

### ③ 첨삭 워크플로

팀 설계 §5.3의 8단계를 따른다. 단계별 근거와 구현 세부는 다음과 같다.

**3-1. 의도·보존 항목 추출**
- 의도: 부탁 / 거절 / 사과 / 일정 조율 / 보고 / 기타
- 보존 항목: 날짜·시각, 수량·금액, 사람, 가능/불가, 약속, 조건, 부정 표현
- 규칙(정규식·날짜 파서)을 먼저 적용하고, 구조화 출력 모델로 보완한다. 두 결과가 다르면 둘 다 보존 대상에 넣는다 (누락이 오탐보다 위험함).

**3-2. 컨텍스트 검색** — 결과마다 `purpose`, `source_message_ids`, `speaker_role`, `sent_at`, `contact_id`를 유지한다.

| 검색 | 대상 | 방법 | 실험 |
|---|---|---|---|
| 페르소나 | persona_versions 현재 버전 | 정확 조회 | B~D |
| 문체 예시 (`style`) | 같은 상대에게 쓴 **본인 발화** 묶음 | 초안+상황 임베딩 kNN [KATE], top-k 3~5 | C~D |
| 사실 맥락 (`context`) | 사용자 그래프의 사건·관계 | Graphiti 하이브리드 검색 (BM25+임베딩+BFS), 상대 노드 거리 재정렬 → 최근성·중요도·관련성 재정렬 | D만 |

D의 재정렬 점수 (Generative Agents 형태, 가중치는 실험으로 조정):
```
score = w_r · 0.995^(경과 시간[h]) + w_i · importance/10 + w_s · relevance
status="open"인 사건 가산 · invalid_at이 있는 사실은 "과거 사실"로 표시
```

**3-3. 프롬프트 조립** — 팀 설계 순서: 시스템 규칙 → 현재 설정 → 원문·최근 맥락 → 검색 예시. 경계를 명시한다.
```
[규칙] 원문의 사실·의도를 바꾸지 말 것. 아래 예시와 맥락은 문체·배경 자료이며 현재 사실의 근거가 아님.
       예시·맥락에 나온 날짜·사유·이름을 원문에 추가하지 말 것.
[설정] 상대: 박지현(상사) · 격식 높음 · 길이 짧게 · 이모지 없음 · 금지: "ㅋㅋ"
[보존] 날짜: 내일 오전 · 약속: 보내드림
[원문] 오늘 정리해서 내일 오전까지 보내드릴게요.
[문체 예시 — style] (10/14) "네 팀장님, 맡겠습니다. 자료는 11월 5일까지 드리겠습니다."
[사실 맥락 — context, D만] (10/5, 해결됨) 일정 조율 중 의견 충돌 → 10/6 사과·합의
```

D의 사실 맥락은 **어조 조정에만** 쓴다 (예: 최근 갈등이 있었으면 더 정중하게). 내용으로 끌어들이지 않는다.

**3-4. 생성** — 구조화 출력 `{rewritten_text, change_reasons, evidence_ids, warnings}`. 서버는 `evidence_ids`가 실제 검색된 동일 사용자 자료인지 검증한다.

**3-5. 검증** — 하나라도 실패하면 실패.

| 검사 | 방법 |
|---|---|
| 보존 항목 대조 | 3-1 항목이 결과에 그대로 있는지 규칙으로 대조 (날짜 정규화 후 비교) |
| 의미 변경 | 부정·가능성·약속·거절 의도 변화 탐지 (규칙 + 보조 모델 판정) |
| 추가된 사실 | 결과에 원문에 없는 날짜·수량·고유명사가 생겼는지 |
| 금지 표현 | 상대별 금지 표현 목록 |
| 근거 검증 | `evidence_ids` ⊆ 실제 검색 결과 |
| 스타일 (보조) | 루브릭 judge [G-Eval]: 격식·호칭·길이·자연스러움. **사실 보존 실패를 상쇄하지 않음** |

모델의 "의미 보존 성공" 자기 보고는 판정에 쓰지 않는다 (팀 설계 §5.3).

**3-6. 분기** — [Self-Refine] 실패 시 **구체적 위반 항목**을 피드백으로 넣어 **최대 1회** 재생성한다. 재실패나 모델 장애가 나면 원문을 유지하고 추천 실패를 표시한다.

**3-7. 사용자 검토** — 추천과 바뀐 부분, 경고를 보여 준다. 적용해도 자동 전송하지 않는다. 요청 중에 초안이 바뀌면 결과를 자동 적용하지 않는다.

### ⑤ 평가

팀 설계 §8 그대로 따른다 (A/B/C/D, 120사례, 사실 보존 98%, 스타일 5점 평균 4, C vs A 선호 60%, Recall@5 0.8, p95 8초).

D 실험에서 추가로 보는 것은 다음과 같다.

| 항목 | 방법 | D 채택 조건 |
|---|---|---|
| 흩어진 사건 연결 | 여러 메시지에 걸친 같은 사건을 맥락으로 써야 하는 사례를 별도 구성 | C 대비 스타일·적합성 개선 |
| 시간·갱신 | 관계가 바뀐 상대 (동기 → 상사)에 대한 첨삭 | 바뀐 관계 기준으로 말투 적용 |
| 맥락 오염 | 그래프 맥락의 날짜·사유가 결과에 새어 들어간 비율 | C보다 높지 않을 것 |
| 비용·지연 | 수집 비용, 요청당 추가 지연 | p95 목표 안에서 감당 가능 |

### ⑥ 실패 유형 점검 (MAST)

다중 에이전트 시스템의 실패는 설계, 에이전트 사이의 어긋남, 검증의 세 묶음 14개 유형으로 정리된다
(Cemri et al., "Why Do Multi-Agent LLM Systems Fail?", NeurIPS 2025 Datasets & Benchmarks). 이 서비스는 다음 단계를
코드가 정하는 고정 워크플로여서 반복과 종료에 관한 유형이 구조상 생기지 않고, 남는 유형은 아래 표로 관리한다.
2.4~2.6을 단계 사이의 데이터 흐름으로 바꿔 읽은 것은 이 문서의 해석이고 논문의 정의와 정확히 같지 않다.

| 유형 | 이 워크플로에서의 모습 | 지금 있는 장치 | 상태 |
|---|---|---|---|
| 1.1 과제 명세를 어김 | 사실을 바꾸거나, 격식·길이·이모지 설정을 따르지 않는다 | `validate_output`(사실), `register_post_check`(반말/존댓말, 플래그) | 일부 빈틈. 길이와 이모지는 검사하지 않는다 |
| 1.2 역할 명세를 어김 | 고쳐 쓰는 대신 초안에 답장을 쓴다 | 없음 | 빈틈. 평가 사례로 확인 필요 |
| 1.3 단계 반복 | 재생성이 끝없이 돈다 | `MAX_REGENERATIONS = 1`, `_attempts_left` | 막힘. `test_fork_after_validate` |
| 1.4 대화 기록 유실 | 재생성 때 원래 프롬프트가 빠진다 | 꼬리말을 `prompt.user` 뒤에 붙인다. 긴 예시는 `fit_examples`가 표시와 함께 자른다 | 막힘 |
| 1.5 종료 조건을 모름 | 모델이 끝을 정하지 않는다 | `_after_generate`, `_after_validate` | 해당 없음 |
| 2.1 대화 초기화 | 에이전트 사이 대화가 없다. 상태는 요청마다 새로 만든다 | 체크포인터 없이 컴파일 | 해당 없음 |
| 2.2 되묻지 않음 | 초안이 모호해도 그대로 고쳐 쓴다 | `ModelOutput.warnings`에 주의점을 적게 한다 | 빈틈. 모호한 초안 사례가 평가에 있는지 확인 필요 |
| 2.3 과제 이탈 | 사실이 아닌 문장을 길게 덧붙인다 | `fact_added`는 날짜·수량·사람만 잡는다 | 빈틈. 길이 비율로 감시 |
| 2.4 정보를 넘기지 않음 | 검색이 실패해 예시 없이 썼는데 결과에 표시가 없다 | `_retrieve_safely`가 경고 로그만 남기고 빈 목록을 돌려준다 | 빈틈. 결과만 봐서는 축소 동작을 알 수 없다 |
| 2.5 입력 무시 | 문체 예시와 말투 지문을 받고도 반영하지 않는다 | `rewrite-v5` 프롬프트의 규칙 10뿐 | 빈틈. 알려진 문제(상대가 달라도 비슷함)와 같은 자리 |
| 2.6 추론과 행동 불일치 | `change_reasons`에 적은 변경이 문장에 없다 | `evidence_ids`가 검색 결과 안에 있는지만 본다 | 빈틈. 사용자에게 보이는 설명이 검증되지 않는다 |
| 3.1 이른 종료 | 출력이 길이 한도에서 잘린다 | 제공자 계층이 `stop_reason == "max_tokens"`를 장애로 올리고 원문을 유지한다 | 막힘 |
| 3.2 검증이 없거나 불완전함 | 말투, 호칭, 추출되지 않는 의미 변화는 통과한다 | 호칭은 `address_leaks` 경고(플래그) | 빈틈. 범위를 문서에 명시 |
| 3.3 잘못된 검증 | 추출기가 잘못 잡아 멀쩡한 결과를 버린다 | `VALIDATOR_VERSION`, `test_validation.py`, `test_preserve.py` | 감시 필요. 원문 유지 사례를 표본 검토 |

빈틈으로 표시한 유형은 평가 결과의 `fm*` 열로 본다(`evals/run_eval.py`의 `failure_signals`, 열 이름의 숫자가
유형 번호다). 모두 참고 신호이고 실패 판정이 아니다. 2.5(상대가 달라도 결과가 비슷함)가 어느 단계에서 생기는지는
`evals/layer_diff.py`로 좁힌다. 2.4를 결과에 드러내려면 응답 형식이 바뀌므로 아직 하지 않았다.

## 5. 기술 스택

팀 설계 §4를 따른다: React + TypeScript, FastAPI, PostgreSQL + pgvector, 고정 워크플로 (LangGraph 상태 그래프, 2026-11-14 도입).
D 실험에서만 **graphiti-core + Neo4j**를 추가한다 (스파이크: Aura Free, OpenAI).

## 6. 구현 순서

| 단계 | 내용 | 기준 |
|---|---|---|
| 1주차 | 범위 확정, 합성 사례 20개, A/B, 상대·프로필 CRUD | 팀 설계 §11 |
| 2주차 | 업로드·화자 지정·묶음·벡터 검색 → C | 팀 설계 §11 |
| 3주차 | 사실 검증·재생성·피드백·삭제·사용량 제어 | 팀 설계 §11 |
| 4주차 | 120사례 평가 (A/B/C) | 팀 설계 §11 |
| **병행** | **graphiti-p0 스파이크**: 한국어 추출 품질·비용 확인 (합성 데이터만) | 코드 작성 완료, 실행은 Aura·키 설정 후 |
| 후속 | D: 첨삭 워크플로에 그래프 맥락 연결, D 평가 | C 대비 개선 + 비용 감당 시 채택 |

스파이크는 본 앱 코드와 분리되어 있어서 1~4주차 순서와 충돌하지 않는다. 스파이크 결과(병합 정확도, 무효화 동작, 에피소드당 비용)로 D 진행 여부를 미리 판단할 수 있다.

## 7. 리스크

| 리스크 | 대응 |
|---|---|
| 그래프 맥락이 원문에 새어 들어감 | 프롬프트 경계 + "추가된 사실" 검사. 맥락은 어조 조정에만 사용 |

| 사용자 격리 | `group_id` 사용자 단위 + 서버 쿼리 템플릿 + 교차 사용자 테스트 |
